## 2. 測定で分かったこと

設計の方向を決めた数字を先にまとめる。

### 2.1 コールド描画の半分はタイルの展開

`verification/cold-render-metal-run1-2026-10-24.json`（4K・半透明 20 レイヤー、ズーム 0.5）の内訳：

| | 時間 |
|---|---|
| コールド描画全体（C3、新経路） | 453.5 ms |
| うちタイル保存からの読み出し（`getMs`） | 227.7 ms |
| うち GPU テクスチャへの書き込み（`writeMs`） | 179.5 ms |
| 読み出したタイル | 2520 枚（660 MB） |

- 展開済みキャッシュ（128 MB）は、1 回の描画で読むタイル（660 MB）より小さい。そのため、CPU キャッシュを残した C2 でも、読み出し時間は C3 と同じ（230.5 ms）になる。キャッシュの大きさを調整しても解決しない。
- WASM 上では、1 タイルの読み出しに約 90 µs かかる。
- ネイティブで内訳を測った（B ベンチマークと同じ模様のタイル、圧縮後 1068 バイト）：LZ4 展開 35.9 µs、圧縮データのハッシュ 1.9 µs、内容ハッシュ 103.7 µs（復旧したタイルの初回だけ）。**重いのは展開そのもの**で、ハッシュ検証ではない。

### 2.2 編集のたびに文書全体を 4 回扱っている

WASM の返信（`envelope()`）は、編集のたびに次を行う。

1. `snapshot()`：文書全体を整形済み JSON に書き出し、ハッシュを取る（`snapshotHash` 用）。
2. `state_hash()`：もう一度 `snapshot()` を書き出してハッシュを取る（保存済みかどうかの判定用）。
3. `version_status()`：最新のコミットを JSON から復元し、作業中の文書と意味的な差分を取る。
4. `state_hash()` の中で、もう一度 `version_status()` を呼ぶ。

B ベンチマークと同じ大きさの文書（4K、20 レイヤー × 135 タイル、コミット 1 つ）でネイティブ計測した結果：

| | 時間 |
|---|---|
| 書き出し＋ハッシュ（254,932 バイト） | 0.95 ms |
| `version_status()` | 1.08 ms |
| **1 回の返信の合計** | **4.07 ms** |

WASM はこれより遅く、レイヤーやテキストが増えるほど比例して重くなる。描画のための処理ではなく、返信を作るためだけの処理である。

### 2.3 JSON という形式は主因ではない

- 毎フレームの `tick()` の返信は、数値が数十個の JSON で、数百バイトである。
- 編集の返信（`patch`）で重いのは、2.2 の付帯情報と、変更されたラスターレイヤーのタイル一覧（1 レイヤーあたり約 13 KB の JSON）である。
- 文書を開いたときの `view()` は文書全体（約 255 KB）を送る。

形式を JSON から変えても、送る量が同じなら効果は小さい。**送る量と、返信のために行う計算を減らすほうが先**である。

### 2.4 保存処理の現状

- Worker の処理ループ（`drain()`）は、編集のたびにジャーナルの書き込み完了（`flushJournal()`）を待つ。待っている間は描画が進まない。
- チェックポイントは、毎回パッケージ全体を 1 つのレコードとして書く。CRC32 は JS のバイトごとのループで計算する。チェックポイントを書くのは、新規作成・コミット・版の整理・開く・保存の確定のときだけで、自動では書かない。保存もコミットもせずに作業を続けると、ジャーナルが際限なく伸びる。
- ストレージ Worker は、チェックポイント全体（`active.base`）とその後の全レコード（`active.records`）をメモリに保持する。
- 復旧では、レコードを 1 件再生するたびに `refresh()` と `view()`（文書全体の JSON）を実行する。
- チェックポイントは取り消し履歴を持たない。そのため、復旧するとチェックポイント以前の取り消し履歴が消え、コミット用の編集記録（intent log）も失われる。
- undo / redo は、「Undo」「Redo」という名前の通常の編集としてジャーナルに記録される。

### 2.5 ブラウザでのスレッド

- Playground は、ページをほかのオリジンから分離する設定（cross-origin isolation）になっていない（`crossOriginIsolated: false`）。そのため `SharedArrayBuffer` が使えず、WASM のスレッドも使えない。
- WASM のスレッドを使うには、標準ライブラリを atomics 付きでビルドし直す必要がある（Rust の nightly 版と `-Z build-std`）。このプロジェクトは Rust 1.99.1 の安定版に固定し、WASM をバイト単位で再現できるようにしている。

## 3. 全体の方針

1. **依存を正しい向きに直す（A）。** 機械的な変更なので最初に行う。以後の変更の土台になる。
2. **返信のための計算をやめる（E の前半）。** 測定で一番無駄が大きく、変更範囲も小さい。
3. **保存処理を描画から切り離し、チェックポイントを増分にする（C）。**
4. **チェックポイントに取り消し履歴を含める（D）。** C で作るチェックポイント形式に載せる。
5. **タイルの展開を並列にする（B）。** 効果は推定値なので、先に試作で確かめる。

各段階を、別々のコミットとプルリクエストにする。どの段階でも、ブラウザの機能テストと、B1〜B7 の計測で悪化がないことを確かめてから次に進む。

## 4. A：クレート構成

### 現状

`alto-engine` は `alto-gpu`（wgpu を含む）に依存している。理由は 2 つだけである。

- 描画シーンの型（`RenderScene`、`RNode`、`RContent`、`RFeatures`、`REffect`、`REffectKind`、`RMask`、`RenderTile`、`RenderBlend`）を組み立てるため。
- 行列計算（`alto_gpu::renderer::{multiply, inverse, point}`）を使うため。これらは `alto_core::Affine2` の `concat` / `inverse` と同じ計算である。

`alto-gpu/src/lib.rs` のうち、型定義、描画計画（`RenderScene::compile`、`RenderPlan`、`Pass`）、第 1 段階の `damage.rs`、`glyph_atlas.rs` は、GPU を使わない。`ResourceManager` は、そのファイル自身のテストからしか使われていない。

### 設計

新しいクレート **`alto-scene`** を作り、GPU を使わない部分を移す。

```
alto-core ─┬─ alto-raster ─┬─ alto-doc ─── alto-engine ──┐
           ├─ alto-vector ─┤                            ├─ alto-wasm
           └─ alto-text ───┘   alto-scene ─┬────────────┘
                                           └─ alto-gpu ──┘
```

- `alto-scene` に移すもの：描画シーンの型、`RenderScene::compile` と描画計画の型、`damage.rs`（`scene_damage`、`plain_scene`）、`cache_allowance`。依存先は `alto-core`、`alto-raster`、`alto-vector` だけとする。
- `alto-gpu` は `alto-scene` に依存し、移した型を `pub use` で再公開する。これは移行期間のためで、次の段階で再公開をやめる。
- `alto-engine` の依存から `alto-gpu` を外し、`alto-scene` に置き換える。
- 行列計算は `alto_core::Affine2` に一本化する。`Affine2::apply(self, p: [f64; 2]) -> [f64; 2]` を追加し、`alto_gpu::renderer::{multiply, inverse, point}` と、エンジンに散らばった同じ計算を置き換える。描画器の内部では `[f64; 6]` のまま使い、境界で `Affine2(..)` に包む。描画器の内部まで書き換えると、この段階の差分が大きくなりすぎるため。
- `ResourceManager` は、使われていないことを確かめてから削除する。
- `glyph_atlas.rs` は描画器しか使わないので、`alto-gpu` に残す。

### 完了の条件

- `cargo tree -p alto-engine | grep wgpu` が何も出力しない。
- `alto-engine` のテストが、wgpu をビルドせずに実行できる。
- 出力される WASM の振る舞いは変わらない。ブラウザの機能テストが全件通る。

## 5. E：WASM との受け渡し

### 方針

JSON を全面的にバイナリ形式に置き換えることはしない。2.3 のとおり、効くのは形式ではなく、送る量と返信のための計算である。変更は次の 3 つに絞る。

### 5.1 返信の付帯情報を差分で更新する（最優先）

- **`snapshotHash` は要求されたときだけ計算する。** 編集の返信からは外し、`view()`、保存、コミットのときだけ計算する。SDK の `DocumentHandle.snapshotHash` は、値が古い可能性があることを型に表す（`snapshotHash: string | null`、編集後は `null`）。値が必要な呼び出し側は `await doc.snapshotHash()` で取得する。
  - **ここは SDK の公開 API の変更になる。判断を仰ぐ点 1（10 章）。**
- **保存済みかどうかの判定（`dirty`）を、ノード単位のハッシュで行う。** 各ノードの内容ハッシュをキャッシュし、`ChangeSet.nodes` に含まれるノードだけを計算し直す。文書全体のハッシュは、ノードハッシュを木の順に並べたものから計算する（Merkle 方式）。保存したときのハッシュと比べれば、undo で保存時の状態に戻ったときも `dirty: false` になる。このハッシュは状態の識別にだけ使い、ファイル名の `snapshots/<hash>` には使わない。
- **版の状態（`version_status`）は、最新コミットの文書を一度だけ復元してキャッシュする。** 計測すると、差分の計算そのものは 0.11 ms で、残りの約 1 ms は毎回スナップショットを JSON から復元し、作業中の文書を複製する処理だった。そこで、コミットまたはパッケージを開いて最新コミットが変わったときに一度だけ復元し、作業中の文書は参照のまま比べる。ノード単位で差分を作り直す仕組みは要らなかった。版の状態は、1 回の返信で 1 度だけ計算する（以前は 2 度）。
  - 実装で変えた点：当初はノードごとの差分結果をキャッシュする案だったが、上の計測を受けて、より単純なこの方法にした。

目安：B ベンチマークと同じ大きさの文書で、1 回の返信の付帯情報が 4 ms から、変更したノード数に比例する時間（1 レイヤーなら 0.1 ms 未満）になる。数値は実装後に計測して確認する。

### 5.2 ラスターレイヤーのタイル一覧を毎回送らない

- 編集の返信では、ラスターレイヤーの `tiles` を、タイル数と範囲だけの要約（`{format, count, bounds}`）に置き換える。
- タイル一覧が必要な呼び出し側のために、要求 `nodeTiles(id)` を追加する。
- SDK の内部（`TransactionBuilder`）は、読み込んだ画像のタイル一覧を自分で持っているので、影響を受けない。Playground の UI は、選択範囲のタイル数しか使っていない。
- **ここも SDK の公開型（`NodeView.tiles`）の変更になる。判断を仰ぐ点 1 に含める。**

### 5.3 毎フレームの返信を固定長の数値配列にする

- `tick()` は JSON 文字列の代わりに、`Float64Array` に固定の順序で数値を書いて返す。順序は Rust 側の `FRAME_FIELDS` の 1 か所だけで定義し、Worker は起動時に `frameFields()` でその名前の並びを受け取って、以前と同じ形のオブジェクトに戻す。
  - 実装で変えた点：当初は両側に定数を置いてテストで一致を確かめる案だったが、並びを 1 か所に置けば食い違いようがない。
- 文字列のフィールド（`adapter`）は、初期化時に一度だけ渡す。
- 効果は小さい（1 フレームあたり数百バイトの JSON の生成と解析がなくなる）。ただし、ほかの項目とは独立していて安全なので、ついでに行う。

### 変えないもの

- 編集操作（ops）の受け渡しは JSON のままにする。利用者が組み立てるデータで、スキーマの変更が追いやすく、デバッグしやすいため。サイズも小さい。
- ジャーナル、パッケージ、ブラシの入力は、すでにバイナリ（`Uint8Array` / `Float32Array`）である。

## 6. C：保存処理と描画の分離、増分チェックポイント

### 6.1 ジャーナルの書き込みを、別の非同期処理（ポンプ）に分ける

- `drain()` は、ジャーナルの書き込みを待たない。編集の処理は、ジャーナルのレコードを書き込み待ちの列に積むだけにする。別の非同期処理（ジャーナルのポンプ）が、列から順に 1 件ずつ書き込む。
- 書き込みの順序は、編集の順序と常に一致させる。チェックポイントの要求も同じ列に積み、それより前のレコードの後に書く。
- **書き込みが追いつかない場合の上限（バックプレッシャー）：** 書き込み待ちが 64 MB または 256 件を超えたら、次の編集は空きができるまで待つ。描画はその間も続く。
- **書き込みの失敗：** 失敗した時点で、これまでどおり `storageFailure` で編集を止め、メモリ上の内容は緊急書き出しで取り出せるようにする。失敗した編集はメモリ上にはすでに適用されている。これは現在の設計（「メモリ上の状態はジャーナルより先に進みうる」）と同じ扱いである。
- **SDK から見た約束（`transact()` の Promise）：** メモリ上に適用された時点で解決する。ジャーナルへの書き込み完了は、新しい `doc.durable()`（その時点までに行った編集がすべて書き込まれたら解決し、書き込みに失敗したら STORAGE で失敗する Promise）で知らせる。
  - 実装で変えた点：revision 指定と `saveState` イベントは作らなかった。編集は順に書き込まれるので、「今までの編集すべて」を待てれば足りる。`durable` 要求は Worker の処理の列に入れずに答えるので、待っている間も編集と描画は止まらない。
  - **これは SDK の振る舞いの変更である。判断を仰ぐ点 2（10 章）。** 現在の `transact()` は、書き込み完了まで待ってから解決する。
- 故障を注入するテスト用の仕組み（`injectedStorageFault`）はポンプの中に移し、既存のテスト（追記の失敗、返信の喪失）が引き続き同じ状況を作れるようにする。

### 6.2 チェックポイントを増分にする（OPFS の構成を変える）

OPFS の構成を、すでにあるフォルダ形式（`alto_store::folder_entries`、内容のハッシュを名前にしたオブジェクト）に合わせる。

```
alto-recovery/
  objects/ab/abcdef…      内容のハッシュが名前。一度書いたら変えない
  manifest-a.json         世代番号、スナップショット、版、履歴、オブジェクト一覧、自身のハッシュ
  manifest-b.json         a と交互に書く
  journal-<世代>.bin       その世代のチェックポイント以降のレコード
```

- **ジャーナルのレコードには、オブジェクトを埋め込まない。** 編集で生まれたオブジェクトは、先に `objects/` に書いてフラッシュする。レコードは、そのハッシュだけを参照する。オブジェクトは名前で中身を検証できるので、書きかけのオブジェクトは復旧時に検出して捨てられる。
- **チェックポイント：** まだ書いていないオブジェクトだけを書き、スナップショット・版・履歴と、到達可能なオブジェクトの一覧をマニフェストに書く。マニフェストを交互の 2 か所に書き、最後にフラッシュする。マニフェストが完全に書けた時点で、新しい世代が有効になる。
- **不要なオブジェクトの削除：** 新しいマニフェストを書いた後、新旧どちらのマニフェストからも参照されないオブジェクトを削除する。前の世代へ戻れるように、1 世代前の参照も残す。
- **自動チェックポイント：** ジャーナルが 32 MB または 500 件を超えたら、手が空いたときにチェックポイントを書く。実行するのは、編集が 2 秒以上来ず、描画も落ち着いているときとする。
- **整合性の検証：** オブジェクトは名前（ハッシュ）で、マニフェストは自身のハッシュで、ジャーナルのレコードはこれまでどおり CRC32 で確かめる。CRC32 の計算は WASM 側で行うか、オブジェクトを外したことでレコードが小さくなるので JS のままでもよい（実装する人に任せる）。
- **ストレージ Worker のメモリ：** チェックポイント全体とレコードをメモリに保持するのをやめる。復旧のときだけファイルから読む。

### 6.2 の実装で変えた点

- **ファイルの構成：** 新しいファイル名（`manifest-a.json` など）は作らなかった。既存の交互に使う 2 つのジャーナル（`journal-a.bin` / `journal-b.bin`）に、新しいレコードの種類（タグ 3）を加えた。タグ 3 には、マニフェスト（`format: 3`、エントリのハッシュ、参照するオブジェクトの一覧、不透明タイルの一覧）と、オブジェクトを除いたパッケージのエントリが入る。オブジェクトは `objects/ab/<ハッシュ>` に置く。世代番号の付け方、交互の書き込み、前の世代への切り替え、故障注入のテストは、そのまま使える。旧形式のファイルも読めるので、次のチェックポイントで自然に新形式へ移る。
- **ジャーナルのレコードには、オブジェクトを埋め込んだままにした。** 「先にオブジェクトを書き、レコードはハッシュだけを参照する」案は採らなかった。書き込み順の管理が増え、クラッシュ時の整合性を崩す余地が増えるため。埋め込んでも、チェックポイントのたびに全オブジェクトを書き直す問題は解消する。代わりに、ジャーナルに記録した編集のオブジェクトは、次のチェックポイントでもう一度書かれる。
- **不要なオブジェクトの削除は、起動時だけにした。** 作業中に削除すると、次のチェックポイントが「書き込み済み」と判断して省いたオブジェクトを消してしまう競合が起こりうる。起動時には、有効なチェックポイントのどれからも参照されないオブジェクトを削除する。書き込みの途中で止まった壊れたファイルも、ここで片付く（マニフェストは、オブジェクトを書いてフラッシュした後にしか書かないため）。
- **書き込み済みオブジェクトの一覧：** ストレージ Worker が起動時に、有効なチェックポイントが参照するオブジェクトを数え、エンジンに渡す（`noteStoredObjects`）。エンジンは、チェックポイントに入れたオブジェクトを書き込み済みとして数える。書き込みに失敗するとストレージ全体が止まるので、数え違いが後のチェックポイントに残ることはない。ストレージ Worker は、チェックポイントが参照するオブジェクトがすべてそろっていることを、書き込みの前に確かめる。
- **保存のたびのパッケージのコピーをなくした。** 保存の確定時のチェックポイントは、現在の状態から変更分だけを書く。Worker は保存のたびにパッケージ全体を保持しなくてよくなった。
- **自動チェックポイントの「止まっている」の判定：** ページは毎フレーム `tick` を送るので、メッセージの有無ではなく、描画以外のコマンドが 2 秒来ないことで判定する。
- **ストレージ Worker のメモリ：** 起動時に読んだチェックポイントとレコードは、復旧するかどうかが決まった時点（`activate` または最初のチェックポイント）で手放す。

### 6.3 復旧の高速化

- 復旧では、全レコードを再生した後に `refresh()` と `view()` を 1 回だけ実行する。新しい要求 `replayRecords(records[])` を追加する。

### 6.4 互換性

- 旧形式（`journal-a.bin` / `journal-b.bin`、マニフェストなし）が残っていたら、旧形式として読んで復旧し、すぐに新形式でチェックポイントを書く。これは現在の V1 から V2 への移行と同じ扱いである。
- `.alto` ファイルの形式は変えない。

## 7. D：復旧後の取り消し履歴

### 設計

- **履歴をチェックポイントに保存する：** マニフェストに履歴を記録する別ファイル（`history-<ハッシュ>.json`）を加える。中身は、`Editor` の `undo`・`redo`・`seq`・`log`（コミット用の編集記録）と、`max_undo` である。`Transaction` はすでに serde で保存できる。
- **履歴が参照するオブジェクトを保存する：** 履歴だけが参照するタイル（`MAX_HISTORY_ONLY_OBJECTS` = 2048 個まで）も、チェックポイントのオブジェクト一覧に含める。現在の `package_parts()` は、文書と版が参照するオブジェクトしか含めていない。
- **ジャーナルのレコードに種類を持たせる：** `{"kind": "transact" | "undo" | "redo", "intent", "ops", "after": <状態ハッシュ>}` とする。`after` には、5.1 の Merkle 方式による適用後の状態ハッシュを入れる。
- **再生のしかた：**
  - `undo` / `redo` は、`Editor::undo()` / `redo()` として再生する。
  - 再生後の状態ハッシュが `after` と一致しない場合は、その場で再生を止め、警告を付けて、そこまでの状態で復旧する。黙って続けない。
  - 履歴を持たない旧形式のチェックポイントでは、これまでどおり ops を通常の編集として再生する。

### 実装で変えた点

- 履歴は別ファイルではなく、チェックポイントのエントリ `history.json` として持つ。マニフェストのハッシュが、ほかのエントリと一緒に守る。
- `max_undo` は保存しない。定数（100）で、復元するときに超えた分を古い順に落とす。
- `after` には、第 2 段階 E で入れた文書の内容ハッシュ（Merkle 方式）を使う。版の head は含めない。版の操作はジャーナルを通らず、チェックポイントで保存されるため。
- 再生結果が `after` と食い違ったときは、その 1 件を取り消してから止める（undo は redo で、redo は undo で、通常の編集は undo で戻す）。通常の編集を戻した後の redo の項目は捨てる。編集を再生した時点で、それ以前の redo はすでに消えているため、完全には元に戻らない。
- 1 件ずつ再生する WASM の関数（`replayRecord`）は使われなくなったので削除した。

### `.alto` ファイルに履歴を含めるか

含めない。復旧のためのチェックポイントにだけ含める。取り消し履歴はファイルを開き直すと消えるのが一般的な振る舞いで、ファイルサイズも大きくなるため。**判断を仰ぐ点 3（10 章）。**

### 完了の条件

- 次の手順を、ブラウザのテストで確かめる。編集 → チェックポイント → 編集 → undo → Worker を落とす → 復旧。復旧後に undo / redo を最後まで繰り返し、各段階のピクセルとスナップショットが、クラッシュしなかった場合と一致すること。
- コミット用の編集記録が、チェックポイントの前後で失われないこと。

## 8. B：タイル展開の並列化

### 8.1 タイル保存を 2 つに分ける（先に行う。単独でも価値がある）

- **`ObjectStore`：** 圧縮済みのオブジェクトを保持する。読み出しで内部の状態を変えない。`HashMap<ContentHash, Arc<StoredTile>>` で、`StoredTile.verified` は `AtomicBool` にする。スレッド間で共有できる（`Send + Sync`）。退避用の `cold` も、この中の状態の 1 つにする。
- **`DecodeCache`：** 展開済みのタイルを LRU で保持する。`&mut self` で操作し、`RefCell` は使わない。描画器とエンジンの CPU 編集が、それぞれ自分のキャッシュを持つ。
- **`decode(&StoredTile, hash) -> Result<TileData, TileError>`：** 状態を持たない関数にする。
- `TileStore` トレイトは `fn object(&self, h) -> Option<Arc<StoredTile>>` と `is_opaque` だけにする。展開は呼び出し側が自分のキャッシュを通して行う。

これで、第 1 段階で残っていた「読み出しのたびに内部の状態が変わる」問題がなくなる。

### 8.1 の実装で変えた点と、分かったこと

- **描画器は展開済みキャッシュを持たない。** GPU のアトラスがキャッシュの役目を果たし、測定でも CPU 側のキャッシュは描画器に効いていなかった（C2 と C3 が同じ時間）。キャッシュを持つのは、ピクセル単位で読む CPU 編集だけで、エンジンが自分で持つ。エンジンは単一スレッドで動くので、このキャッシュだけは `RefCell` に置いた。共有される `ObjectStore` は内部の可変性を持たない。
  - 効果：B6 の WASM のメモリのピークが 241 MiB から 170 MiB に減った。
- **トレイト `TileStore` から `put` を外した。** 読み出し側（描画器）しか使っていなかった。
- **オブジェクトの書き出しで展開しない。** 保存してある圧縮データの形式（LZ4 の長さ付き）は、パッケージのオブジェクトの形式と同じなので、ヘッダーを付けるだけで書き出せる。一度も内容の検証をしていないタイルだけは、先に検証する。ジャーナルの記録、チェックポイント、保存が、タイルの展開と再圧縮をしなくなった。
  - 効果：B5 の保存が 278 ms から 21 ms、開く処理が 1079 ms から 817 ms、B4 が 6.4 ms から 3.2 ms になった。後の 2 つは、開いた直後と取り消しの後のチェックポイントが軽くなったため。
- **C2 で増えていた復旧の時間を減らした。** 起動時のオブジェクトの一覧作成と不要オブジェクトの削除を、起動後の最初の書き込みの直前に移した。また、復旧の候補を新しい世代から 1 つずつ読み、古い世代のオブジェクトを読まないようにした。
  - 効果：B7 が 2172 ms から 1465 ms になった。ただし C2 の前（約 1270 ms）より約 150 ms 遅い。オブジェクトを 1 ファイルずつ読むため（約 2700 ファイルで約 200 ms）。同期アクセスのハンドルで読むと、かえって遅かった（約 460 ms）。縮めるには、オブジェクトをまとめて 1 つのファイルに詰める形式が必要になる（後続の課題）。

### 8.2 まとめて展開する経路を作る

描画器の表示ジョブは、計画を立てた時点で必要な入力タイルの一覧（`TileJob.unique`）をすべて知っている。そこで、ジョブの段階に「入力の展開待ち」を加える。

1. 計画を立てる → 入力の一覧が決まる。
2. アトラスに無い入力をまとめて展開器に渡す（`DecodeRequest { hashes, compressed: Vec<Arc<StoredTile>> }`）。
3. 展開が届いたものから GPU に書き込む。
4. すべてそろったら合成する。

展開器は、環境ごとに次のように実装する。

- **ネイティブ：** `std::thread::scope` で、コア数ぶんに分けて展開する。
- **ブラウザ：** 展開専用の Worker を 2〜3 個置く（`DecodePool`）。各 Worker は、LZ4 と BLAKE3 だけを含む小さな WASM（新しいクレート `alto-decode`）を読み込む。圧縮データ（数 KB）をコピーして渡し、展開結果（256 KB）は転送可能な `ArrayBuffer` で受け取る。受け取った展開結果は描画用 WASM のメモリにコピーしてから、GPU に書き込む。
- **同期経路（参照用）：** 展開器を使わず、その場で展開する。テストでの比較と、Worker を起動できない環境のために残す。

### 8.3 採らなかった案

- **WASM のスレッドと `SharedArrayBuffer`：** cross-origin isolation が必要で、エンジンを組み込む側のページにヘッダー設定を強いる。さらに Rust の nightly 版が必要で、固定した安定版と、WASM のバイト単位の再現性を失う。
- **キャッシュを大きくする：** 1 回の描画で 660 MB 読むため、効果がない（2.1）。
- **GPU 上で展開する：** LZ4 は逐次的な形式で、並列に展開しにくい。タイルの形式から変える必要があり、範囲が大きすぎる。

### 8.4 効果の見積もりと試作

- 見積もり（推定値）：展開器が 3 つの場合、読み出しにかかる時間（`getMs`、約 230 ms）は、受け渡しとコピー（1 タイル約 25 µs × 2520 枚 ≈ 63 ms）程度まで下がる。コールド描画は約 450 ms から約 330 ms になる。
- この数字は推定である。8.1 の分割を終えた後、ブラウザ用の展開 Worker を最小限で試作し、C3 で効果を測る。改善が 15% 未満なら 8.2 のブラウザ用実装は行わず、8.1 とネイティブの並列化だけで止める。

## 9. 検証

- 各段階で、Rust のテスト、clippy（ホスト用と wasm32 用）、`scripts/check.sh`、ブラウザの機能テスト（Metal と SwiftShader）を通す。
- 各段階で、B1〜B7 を変更前と変更後で 10 回ずつ交互に計測する（第 1 段階の比較と同じ手順）。
- 新しく、編集後の再描画の時間を測る計測 **B8** を加える。内容は、表示済みの 4K・20 レイヤーで 1 タイルぶんを塗り、描画が落ち着くまでの時間である。第 1 段階の差分描画と、5.1 の効果を数字で示すため。
- C と D では、故障注入のテスト（追記の失敗、返信の喪失、書きかけのオブジェクト、壊れたマニフェスト）を新しい構成で全件作り直す。

## 10. 判断を仰ぐ点

いずれも、SDK を使う側から見える振る舞いが変わる。

1. **編集の返信を小さくする（5.1、5.2）。** 返信に `snapshotHash` とラスターレイヤーのタイル一覧を含めない。`DocumentHandle.snapshotHash` と `NodeView.tiles` の型が変わる。
2. **`transact()` の Promise を、メモリ上に適用された時点で解決する（6.1）。** ジャーナルへの書き込み完了は `doc.durable()` で知らせる。変えない場合は、描画は止まらなくなるが、編集の Promise の解決は今と同じく遅いままになる。
3. **取り消し履歴は復旧用のチェックポイントにだけ含め、`.alto` ファイルには含めない（7 章）。**

## 11. 実装する人に任せること

- バックプレッシャーの上限（64 MB / 256 件）と、自動チェックポイントの条件（32 MB / 500 件 / 2 秒）。測ってから調整してよい。
- 展開 Worker の数（2〜3）。
- ジャーナルの CRC32 を WASM で計算するか、JS のままにするか。
- 移行期間中の `alto-gpu` からの再公開を、いつやめるか。
