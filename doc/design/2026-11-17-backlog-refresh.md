# 未実装機能の設計書を今のコードに合わせて書き直す

作成日：2026-11-17。基点は main `bdf26a9`。

状態：設計（この書き直し作業の進め方）。

## 目的

`doc/design/backlog/` の13本（2026-11-04、main `b2036ce` 時点）は、その後の146コミット（堅牢化 A〜F、版を `.alto` の外に持つ F-9 など）で古くなった。
計画に残る82項目のすべてを、**今のコードのまま実装に着手できる細かさ**に書き直す。

利用者の決定（2026-11-17）：対象はすべて。方式は「今ある13本を書き直す」（案 A）。

## 目標と範囲

- 対象：計画に残る82項目。`00-ROADMAP.md` と 01〜13 の各文書。
- 除外の8項目（UI-1〜5、SEL-4、AI-2、AI-3）は「実装しない」の決定を変えない。記録の事実だけを直す。
- コードは1行も変えない。

## しないこと

- 新しい項目を足さない（PDF/SVG 書き出しなどの計画外の欠けは、末尾の「計画外の候補」に列挙するだけ）。
- 測定前に速度の約束を書かない。「先に測るもの」の判定条件は残す。
- 利用者の決定が要る点（D4、D6 など）を勝手に決めない。案と既定を書いて残す。

## 各項目に必ず書くこと

1. **現状**：今の main で関係するファイル・型・関数。パスと名前は実在を確かめたものだけ書く。新しく作るものは「新規」と明記する。
2. **11-04 からの変化**：古い記述のどこが変わったか（無ければ「変化なし」）。
3. **設計**：データの形、API（Rust と SDK）、アルゴリズム、上限の定数、エラーコード。
4. **形式と通信**：`format_version`、`PROTOCOL`、manifest、描画の版（v3/v4）に触れるか。触れるなら共通規則3に従う。
5. **作業手順**：ファイル、インターフェース、試験名と確かめる内容、完了条件、検証コマンド。
6. **依存**：先に要る項目と、後に続く項目。

## 文書をまたいで揃えるもの

各文書を書いたあと、`00-ROADMAP.md` で次を一つの表にまとめ、重なりを解く。

- シェーダーのモード番号（34 から）。
- `format_version` と `PROTOCOL` を上げる項目と、まとめる単位。
- 依存の順序（今の「実装の順序」を更新）。
- 段階・工数の見直し（変わったものだけ、理由つき）。

## 進め方

1. 領域ごとに調査役（サブエージェント）を1人ずつ割り当て、今のコードを読んで1本を書き直させる。コードは変えない。
2. 書き上がった文書ごとに、私が次を確かめる。
   - 書かれたパスと名前が main に実在するか（機械的に確かめる）。
   - 「各項目に必ず書くこと」が全項目にそろっているか。
3. 文書ごとに opencode で読み取り専用のレビューを行い、指摘はコードで確かめてから直す。
4. 最後に `00-ROADMAP.md` を更新し、文書間の重なりを解く。
5. 1本のブランチに文書ごとに1コミットで積み、PR は利用者の指示を待つ。
6. 進捗は文書が1本終わるたびに日本語で短く報告する。

## 完了条件

- 82項目のすべてに「各項目に必ず書くこと」の6点がある。
- 文書中のパスと名前が、作業の基点の main に実在するか「新規」と明記されている。
- モード番号・形式番号の割り当てに重なりがない。
- 各文書の冒頭に基点のコミットが書いてある。

## 私が決めたこと（確認してください）

- 文書の構成（領域ごと13本＋ROADMAP）は変えない。
- PR は1本にまとめ、コミットを文書ごとに分ける。レビューは文書ごとに行う。
- 計画外の欠け（PDF/SVG 書き出し、OSフォントなど）は項目にせず、候補として列挙だけする。
