## A：基準となる検証を完走する

- 同じコミットで次を実行し、各コマンドの終了コードとログを保存する。
  - `sh scripts/check.sh native`（fmt・workspaceテスト・clippy）
  - `sh scripts/check.sh wasm-fast`（WASM/SDK。キャッシュ済みビルドを使い、releaseハッシュのずれは報告のみ）
  - `node scripts/verify-browser.mjs --functional`（ハードウェア依存のB1〜B7ベンチマークを除く機能試験）
- ブラウザ試験の出力は `verification/out/`（`ALTO_BROWSER_REPORT_DIR` で変更可）の `summary.json` を保存する。予期しないGPUプロセスのクラッシュはここに記録されるので、試験失敗と区別して扱う。
- 長時間テストは進行とCPU/GPUの状態を確認する。時間がかかるという理由だけで失敗やハングと判定しない。タイムアウトした場合は未完了として、対象テストを単独で切り分ける。
- 実行コミット、Rust・Node・ブラウザのバージョン、OS、GPU/バックエンド、成功・失敗・スキップ・中断の件数を記録する。

完了条件：3コマンドすべての終了結果がある。未完了を合格に含めない。既存の失敗は再現条件と担当経路を明らかにしてから変更に進む。releaseハッシュの厳密な検査はFで行う。

## B：CPU合成経路を削除する

対象：`crates/alto-engine/src/edit.rs`、`lib.rs`。

調査結果から、`export_rgba` / `sample_pixel` は呼び出し元がなく、SDKにも公開されず、Rustクレートは配布されていない。対応範囲もSDKの書き出しより狭い。維持すると座標の欠陥を直したうえで、GPU経路との二重保守が残る。よって削除を既定とする。

- `export_rgba`、`sample_pixel` と、それらだけが使う `translation` / `chain` / `read_pixel` / `mix_mode` / `composite_pixel` / `straight` / `draws` / `pixel_at` を削除する。
- `edit.rs` 内のテスト（例：`overlay_reaches_the_renderer_and_levels_bump_the_format`）は2メソッドを呼んでいない。対象の機能に合うモジュールへ移し、`mod edit` が空になれば削除する。
- 描画の独立したCPU参照は `crates/alto-gpu/src/cpu_composite/` と `tests/e2e/cpu-composite.js` にある。今回削除するのはエンジン側の未使用経路だけで、これらは残す。
- API削除をPRに記載する（未リリースのため移行手順は不要）。

削除に反対する利用者・用途が見つかった場合だけ、次の修正で維持する（別PR）。

- `translation`：丸め後の値がi32の範囲にあるかを検査してから変換する。
- `chain` と `pixel_at`：親子の累積と画素−オフセットをi64で計算し、i32に収まらなければ範囲外（透明）とする。範囲外とエラーの条件をRustドキュメントに書く。
- `read_pixel` を `image::read` に置き換え、タイル形式の検査を共有する。
- 出力バッファは `try_reserve` で確保し、確保失敗をエラーにする。
- 試験：i32最小・最大とその外側、正負の巨大な有限値、親子の累積と相殺、負のタイル境界、深さ上限（`MAX_TREE_DEPTH` は文書検証と同じホップ数で数える）。debugとreleaseの両方で同じ結果になること。

完了条件：削除した関数への参照が残らず、`check.sh native` が成功する。維持した場合は、上の試験でpanic・折り返し・黙った飽和がなく、通常入力の出力が変わらない。

## C：実際の表示・書き出しの契約を確認する

対象：`packages/alto-sdk/src/document.ts` / `worker.ts`、`crates/alto-wasm/src/`、`alto-gpu` の描画・読み戻し、既存のブラウザ試験（`tests/e2e/parity-tests.js` など）。

1. 契約を先に書く。`exportImage` の `region` / `scale` / `type` について、公開入口からGPU読み戻し・符号化までの経路と対応機能を一覧にする。RGBAのpremultiplied/straight変換、透明画素のRGB、丸め規則、範囲外の領域の扱いを定義する。
2. 正解はキャンバスのスクリーンショットではなく、同じ文書座標・倍率・透明背景条件で得たレンダラー出力とする。CPU参照（`cpu_composite`）との比較が既にある機能は、その結果を再利用する。
3. 最小文書で、17合成モード、半透明、グループ（通過・分離）、マスク、クリップ、効果、テキスト、ベクター、変形、負座標、出力範囲・倍率を確認する。全組合せは作らない。各機能単独と、既知の不一致が起きた組合せ（[semi-transparent-composite-parity](../verification/semi-transparent-composite-parity.md)）を選ぶ。
4. PNGはデコード後の画素を比較する。JPEGなど非可逆形式は、寸法・形式・符号化前の画素を確認する。
5. `pickColor` は合成結果ではなく層の保存画素を返す。層の外の座標が `NOT_FOUND` になること、R8層の値の並びをAPIドキュメントに明記し、試験を加える。合成結果のスポイトが必要なら別計画にする。
6. 不一致は合成、色・アルファ変換、読み戻し、符号化のどこで起きるかを切り分けて修正する。

完了条件：対応範囲の一致条件が文書化され、代表文書がGPU読み戻しとPNG出力で一致する。未対応の入力は部分出力を成功として返さず、契約に沿ったエラーになる。

## D：保存・復旧を障害の境界で検証する

[QA-5](backlog/13-verification.md)の計画に沿って `tests/e2e/crash-tests.js` を新規に作り、`scripts/verify-browser.mjs` に組み込む。対象はSDKの `storage-core.ts` / `storage-session.ts` / `engine.ts`。障害を起こす時点は、SDKの `testing` 入口（`@alto/engine/testing`）に足す待機点で決め、本番の公開APIには足さない。

| 注入箇所 | 確認する保証 | QA-5との関係 |
|---|---|---|
| 未確定ストローク、Transaction確定後・durable前、durable後 | メモリ上の確定と永続化を区別する。durable成功済みの変更は復旧する。durable前は直前の正常な記録まで戻る | 「ストローク中」を3点に分割 |
| ジャーナル追記中 | CRCで不完全な末尾を除外する | 既存 |
| チェックポイント切替中 | 前の世代へ戻る | 既存 |
| `.altoproj` 保存のmanifest確定前後 | 旧版または新版が読め、混在した状態を成功として扱わない | 既存は確定前のみ。確定後を追加 |
| OPFSのGC削除中 | 再試行で全rootのbytes・hashが保たれる | 既存 |
| 版のマージ確定中 | 文書と履歴が整合する | 追加 |
| Worker停止、GPU喪失 | 確定内容が復旧し、状態通知・再試行が契約どおり | 追加 |

- 実施順：既存5行 → 追加行。1行ごとに試験と修正を1PRにする。
- 論理的な書き込みエラーの注入と、CDPの `Target.closeTarget` / `Page.crash` による実際の強制終了を分けて実施する。
- GPUは注入した喪失と予期しない喪失を区別する。復旧が成功しても、予期しない喪失を合格に数えない。

完了条件：各待機点で10回連続成功する。文書のsnapshot hash、参照タイル、版履歴を照合し、正常終了しただけでは合格にしない。外部ハードウェアが必要な試験は未検証として残し、確認した環境を明記する。

## E：性能は使われる経路から測る

- 同じ環境・文書・表示範囲・DPR・ビルド条件で、変更前後を比較する。コールド表示とウォーム操作、ベクターとラスターは分ける。既存のB1〜B7ベンチマーク（`verify-browser.mjs --benchmark-only`）を基準として使い、足りない項目だけ追加する。
- 固定fixture：4Kの単層・20層、疎な大画像、半透明と効果、テキスト・ベクター混在。上限に近い文書はストレス試験として分ける。
- 測る処理：編集確定、初回表示、継続操作、PNG出力、保存、復旧。反復数と全サンプルを保存し、十分な標本がある項目だけp95を示す。
- WASMメモリ、JS heap、GPUリソースの計上値を分けて記録する。計上値を物理VRAM使用量と呼ばない。
- 測定で支配的と分かった処理を1つずつ修正し、画素と文書の整合性を再検証する。
- `DecodeCache` のヒット時の管理処理は、Bで削除した後はスポイトだけが使う。1回の操作で数画素しか読まないため、計測で支配的と分かった場合だけ扱う。

完了条件：環境・入力・サンプルを伴う比較結果があり、改善した処理の時間短縮が測定のばらつきを超える。対象外の処理に再現する劣化があれば、解消するか採用を見送る。測定前に倍率や高速化率を約束しない。

## F：長時間運用と配布物を確認する

- [QA-4](backlog/13-verification.md)の計画に沿って `tests/e2e/soak.js` を新規に作る。固定seedの編集（ブラシ、Undo、変形、効果、コミット、保存）を4時間続け、1分ごとに記録する。
- 判定はQA-4の基準を使う：Undo上限に達した後、GPU計上値とWASMメモリが増え続けない。B1とB3のp95が初期から20%以上悪化しない。ジャーナルが保存で切り詰められる。悪化した場合は入力の複雑化とリークを切り分ける。
- 最後に保存・再読込し、文書・タイル・履歴を比較する。durable済み内容の欠落、予期しないGPU喪失、復旧のループがあれば、未解決のまま出荷判定しない。
- クリーンな作業ディレクトリでWASM/SDKを再ビルドし、`npm pack` したSDKから最小の埋め込み例を動かす。生成物の同梱、API、保存・再読込・PNG出力を確認する。
- ハッシュは `RELEASING.md` の手順（`wasm-hashes-main` の提案値、`sh scripts/update-wasm-sums.sh`）に従う。テストを通す目的だけで基準ハッシュを更新しない。

完了条件：実行コミット・配布物のハッシュ・環境・全試験結果を対応づけた記録がある。「実装済み」「テスト成功」「配布物確認済み」「性能測定済み」「実制作での評価」を別項目で書く。
