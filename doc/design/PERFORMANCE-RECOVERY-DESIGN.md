# 4K 半透明レイヤーの縮小表示・復旧高速化設計

高DPIでのズーム単位とWorker読み込み障害については、[追加設計](DPR-WORKER-RESILIENCE-DESIGN.md)を参照。

状態: 復旧V2とタイル検証の要点を実装し、性能を実測。[結果報告](../verification/PERFORMANCE-IMPLEMENTATION-RESULTS-2026-10-22.md)を参照。以下は当初の設計案で、索引の詳細形式、復旧内部計時、可視タイルバッチ化、先読みは今回の実装とは異なるか未実装。

基準: `026ff48`、Chrome 155 headless / Apple Metal WebGPU、3840×2160、半透明ラスターレイヤー20層。[測定記録](../verification/PERFORMANCE-BOTTLENECKS-2026-10-22.md)では B2 縮小表示 395.1 ms（目標250 ms）、B7 Worker 復旧と初回完全描画 2029.6 ms（目標1500 ms）。B7 の内訳は `openPackage` 799.8 ms、初回描画 1138.0 ms。各条件1回の診断ランなので、ここでの差分は設計の優先順位にのみ用いる。

## 守る契約

1. 保存済みの表示結果と、復旧後の文書状態・画素は一致する。破損したタイルを黙って透明として描画しない。
2. `.alto` ZIP と `.altoproj` の互換性を維持する。外部ファイルは内容ハッシュによる全オブジェクト検証を続ける。
3. 2本のOPFSジャーナル、世代選択、確定済みレコードの再生、不完全な末尾の切り捨てを維持する。高速経路が不適格なら旧経路または前世代へ戻る。
4. 半透明、マスク、ブレンド、効果、Undo/Redo の画素を維持する。高速化のために描画順を変更しない。
5. GPU使用量の推定上限512 MiB、WASM上限1024 MiBを超えない。現在の20層ベンチマークはGPU約484 MiBなので、可視タイルを守りながら既存の256表示スロットを使う。
6. B2/B7は従来どおり `gpuIdle()` 後の完全描画まで計測する。早期プレビューを完成扱いしない。

## A. ブラウザ内チェックポイントの高速復旧

### A1. 信頼の境界

`alto-store::decode_entries` はすべてのオブジェクトを LZ4 展開し、展開後の内容ハッシュを確認する。これは外部入力に適切な検証である。一方、ブラウザ内ジャーナルのチェックポイントは、エンジンが既に検証済みのオブジェクトから作成する。書き込んだ圧縮バイト列が復旧時にも同一だと確認できれば、起動時の全件再展開を省ける。実際に使用するタイルは `MemoryTileStore::get` が従来どおり展開後の内容ハッシュを確認する。

高速経路の前提をコードで強制する。外部ZIPから直接 `open_recovery_checkpoint` を呼べないAPIとし、エンジンが作成したチェックポイントである証明を伴う場合だけ許可する。現行のCRCは事故的な破損検出として維持し、追加するSHA-256はバイト列の同一性確認に用いる。秘密鍵による真正性の保証はこの設計の対象外。

### A2. ジャーナルV2の記録

公開 `.alto` ZIPは変更しない。OPFSのチェックポイントレコードだけを版付けする。概念上の内容は次のとおり。

```text
CheckpointV2 {
  generation,
  package_len,
  package_sha256,
  index_len,
  index_sha256,
  package_bytes,       // 従来と同じ .alto ZIP
  recovery_index {     // このチェックポイントに含まれる全オブジェクト
    snapshot_hash,
    objects: [{ decoded_hash, tag, encoded_len, opaque }]
  }
}
```

`recovery_index` は圧縮済みオブジェクトと同じ文書スナップショットから生成する。不透明判定は展開せずに使うため、保存時に確定した値を保持する。`package_sha256` と `index_sha256` は、書き込み先ジャーナルを有効化する前に計算する。長さ、ZIPエントリー数、名前、パス、重複、展開後サイズの宣言値には現行同等の上限を課す。ジャーナルのレコード長上限とパッケージ上限は明示的に整合させ、確保前に検査する。

保存順は `package + index 作成 → ハッシュ計算 → 非アクティブ側へ書き込み → flush → 世代確定`。既存の交互書き込みを維持し、途中終了時には前世代が残る。

### A3. 復旧の状態遷移

1. `storage-core.js` は両ジャーナルの候補を世代順に保持する。現状のように最新候補だけを選んで古い候補を捨てない。
2. 最新候補のレコードCRC、チェックポイント長、`package_sha256`、`index_sha256` を確認する。失敗時は次の候補へ進む。
3. `alto-store` の `decode_recovery_checkpoint` がZIPの構造と索引の一致を確認し、スナップショット・コミットをハッシュ検証して復元する。オブジェクトはヘッダー・形式・宣言サイズを確認したうえで圧縮状態のまま登録する。全タイルのLZ4展開はここで行わない。
4. 確定済みの追加レコードを順番どおり再生する。追加レコードに含まれる新規オブジェクトは従来の内容ハッシュ検証を通す。末尾破損は既存の警告と有効プレフィックスへの切り捨てを維持する。
5. 文書スナップショットとバージョン履歴に必要な参照を確認してから `recovered` を通知する。候補の検証が失敗した場合は前世代を試す。両候補が失敗した場合は保存障害を表示し、何もない新規文書として扱わない。
6. タイル取得時の展開・内容ハッシュ不一致は `CORRUPT_DATA` として描画と保存に伝播させる。`TileStore::get` が `Option` だけを返す現行契約を、欠損と破損を区別できる `Result<Option<TileData>, TileReadError>` 相当へ変える。タイルを透明に置換して続行しない。

V1ジャーナルは現行の全件検証で読み、次の正常なチェックポイント時にV2へ移行する。外部 `.alto` の `openPackage` は現行経路を使う。両候補のCRC・SHA検証と候補選択を終えるまで、ジャーナルの切り詰めや次の書き込み先確定を行わない。

## B. コールド表示タイルの仕事量削減

### B1. 計測点を先に入れる

`Renderer::compose` の1タイルを「シーン交差判定、タイル取得、LZ4展開、RGBAコピー、`queue.write_texture`、コマンド生成、GPU提出」に分ける。フレームには `atlas_hit/miss/eviction`、CPUタイルキャッシュ hit/miss、転送バイト数、完成済み表示タイルからの縮小成功数を集計する。GPU実行時間は対応アダプターでtimestamp queryが使用できる場合に別計測し、CPUの `gpuIdle()` 待ち時間と混同しない。診断カウンターは通常の描画結果や保存形式に含めない。

### B2. シーン索引とバッチ

`RenderScene` は編集時に更新されており、毎tickの再生成は主因ではない。シーン更新時にレイヤーごとのタイル索引を作り、表示タイルごとに全タイルの `BTreeMap` を作り直す処理を避ける。ストローク中のプレビュー上書きもこの索引に重ねる。

1フレームで不足する表示タイルを中央から順に列挙し、入力タイルの重複ハッシュを集計する。1バッチの固有入力がアトラスの空き・退避可能スロットと出力スロットに収まるように分割する。バッチ内では各入力を一度だけ取得・転送し、複数の表示タイルのコマンドをGPUキューに順序どおり提出する。バッチ内の入力スロットは提出が終わるまで固定し、前バッチの読取より先に上書きされないことをキュー順序のテストで確認する。1表示タイル自体が容量を超える場合は既存のエラーを維持する。

`rgba_pixels` はRGBAタイルにも毎回 `to_vec()` する。RGBAでは元バッファを借用して `queue.write_texture` に渡し、R8だけ変換バッファを作る低リスクの改善を、内訳計測後の最初の小変更として試す。

### B3. 中断可能な表示ジョブと縮小キャッシュ

現行の8 ms予算は `compose` 1枚が8 msを超えても止められない。合成を `計画 → 入力準備 → コマンド作成 → 提出` のジョブに分け、入力準備中は数タイルごとに制御を返す。ペン入力・文書変更・可視領域のジョブを最優先し、先読みジョブは中断可能にする。編集で無効になった領域の先読み結果は採用しない。既存の `invalidate(bounds)` に対応する世代番号をジョブに持たせ、範囲外の有効キャッシュは残す。

操作が落ち着いたときだけ、現在と隣接する縮小段階の表示タイルを既存の256スロット内で先読みする。可視タイルを固定し、先読みが入力遅延やメモリ上限に近づけば停止する。完成済みの子タイル4枚がある場合は既存の `downsample_cached` を使い、足りない場合は計測結果に応じて直接合成または子タイル準備を選ぶ。表示ピラミッドはレイヤー単位ではなく最終合成画像から作る。半透明の合成順と既存シェーダーの画素規則を保持する。

復旧直後はGPUキャッシュが空なので、この先読みだけではB7を解決できない。B7はAの起動短縮とB2のコールド合成削減を合わせて改善する。プレビュー画像の永続化は任意の後続案とし、B2/B7の完全描画目標を満たすまで完成扱いに使わない。

## C. 段階的な実装と合格条件

| 段階 | 完了条件 |
| --- | --- |
| 0. 計測 | `openPackage` と `compose` の内訳、アトラス再転送、縮小キャッシュ命中率がJSONに残り、計測なしビルドで挙動が同じ |
| 1. V2復旧 | V1・V2・外部ZIPを読める。ビット反転、欠損、古い世代、不完全な末尾、追加レコード再生で文書と画素が正しい |
| 2. 描画の小変更 | RGBAコピー省略とシーン索引の各変更を独立ベンチマークし、画素差・B3入力遅延・メモリを確認 |
| 3. バッチとジョブ | 半透明20層のB2/B7を改善。編集、ズーム連打、Undo/Redo、GPU喪失後も古い表示タイルを採用しない |
| 4. 最終検証 | 同一端末・同一Chrome・複数の新規プロファイルで B2 ≤250 ms、B7 ≤1500 ms、B3 p95 ≤33.4 ms、GPU推定 ≤512 MiB、WASM ≤1024 MiB。機能・保存障害・破損復旧のテストがすべて通る |

性能値は中央値だけでなく各ランとp95を保存する。B7は「Worker起動」「チェックポイント検証・展開」「記録再生」「最初の可視フレーム」「完全描画」の時刻を別々に出す。成功判定は完全描画で行い、早期表示の体感改善は別の指標として記録する。

## 最初の実装単位

最初のPRは段階0の計測だけにする。次のPRでV2復旧を実装し、フォーマット移行と破損テストを確定する。その後に描画の小変更を一つずつ測り、結果を見てバッチとジョブ分割を進める。この順序なら、約800 msの復旧処理と描画内部の負荷を独立に評価できる。
