# 過去の版のタイルを必要時に読む

作成日：2026-11-03。状態：実装済み。段階 5「必要タイルだけを保存先から読む」のうち、履歴のタイルを対象とする。

## 1. 目的と範囲

フォルダを開くと、今は全ての版のタイルをメモリへ読む。版が増えるほど開く時間とメモリが増え、ほとんどの編集で使わない。
`engine.openFolder(provider, { history: "on-demand" })` では、現在の文書のタイルだけを読み、過去の版のタイルは必要な操作の直前に読む。

| 対象 | 扱い |
|---|---|
| 作業文書のタイル | 開くときに全部読む |
| Undo/Redo のタイル | 編集中はメモリに残す |
| 版が参照するタイル、フォント、テキストベイク | 保存先に残し、必要時に読む |
| コミット、スナップショットの JSON | 全部読む。履歴表示と差分は画素を読まない |

対象外：表示範囲に応じた作業文書のタイル読み込み。renderer と画像編集の同期経路でタイルを取得する別の設計が要る。既定の `openFolder` は従来どおり全部読む。

## 2. 用語

- **known**：保存先に存在すると分かっている object の集合。開くときの `list("objects/")` と、同じ保存先への保存成功で更新する。
- **external**：文書が参照し、known に含まれ、今はメモリにない object。known に無くメモリにも無い参照は従来どおり破損。
- **pin**：操作の間だけメモリに留める object。

## 3. 必要時の読み込み

SDK は該当操作の前に次の順で進む。一文書の編集キューの中で直列に行う。

1. Worker に対象（commit、ブランチ切替先、マージ、全部）の不足 object を尋ねる。
2. 不足があれば保存先の排他の中で読み、Worker へ渡す。保存先が無ければ `STORAGE`（reason `objects-unavailable`）で、文書は変わらない。
3. Engine が全 object のパス、形式、内容ハッシュを検証してから一括で取り込んで pin する。対象の版の画像範囲とマスク形式も検証する。一つでも不正なら何も取り込まない。
4. 復旧チェックポイントを書き、完了を待つ。これにより、この後の履歴遷移を journal から再生できる。
5. 操作を実行し、pin を解除する。現在の文書と Undo に残らなかった object はメモリから外れる。

| 操作 | 対象 |
|---|---|
| `checkout`、`detach`、`restore`、`createBranch({ checkout: true })` | 対象の commit |
| `prepareMerge`、`finishMerge` | 両 head と共通祖先 |
| `save`、`emergencyExport`、`compactArchive`、別の保存先への `saveFolder` | 全部 |
| 同じ保存先への `saveFolder` | 読まない。external は書き込み済み |
| `log`、`diff`、`status`、`commit` | 読まない |

`save` の後は、同じ保存先にある object だけメモリから外す。未保存のコミットのタイルは保存までメモリに残る。

## 4. 検証

開くときは作業文書を従来どおり検証する。履歴については JSON、DAG、known に全 object があることを確認し、画素は読み込み時に検証する。
破損した履歴 object は開くときではなく、その版を使う時に `CORRUPT_DATA` になる。これが全部読む場合との違いで、この方式の代償である。

## 5. 復旧

チェックポイントは external の bytes を持たず、`lazy-objects.json` に known を記録する。

- **Worker の再起動**：SDK は保存先を覚えているので、そのまま読み込みを続ける。
- **ページの再読み込み**：保存先を自動では持てない。作業文書、Undo、履歴の JSON は復旧する。過去の版のタイルが要る操作は `objects-unavailable` になる。`versions.attachFolder(provider)` で保存先を繋ぐと続けられる。
- **保存先が使えない時の書き出し**：`save` は履歴を黙って省略せず失敗する。`save(target, { history: "omit" })` を明示すると、作業文書だけの `.alto` を書く。

journal に記録した履歴遷移より前に、必要な object を含むチェックポイントが完了している（第 3 節の手順 4）。

## 6. 他の処理による削除

保存先の object に依存し続けるので、実 GC に消されないようにする。

- OPFS：文書が開いている間、フォルダごとの共有 Web Lock を持つ。実 GC は同じ名前の排他ロックを `ifAvailable` で取り、他の文書が開いていれば `BUSY`。自分の共有ロックは GC の間だけ外す。GC は保存済みの全 root を残すので、自分の external は消えない。
- File System Access：他のオリジンやネイティブの GC を止められない。読み込み時に見つからなければ `STORAGE` で、文書は変わらない。作業文書と Undo は影響を受けない。

## 7. 効果

読む object は作業文書の分だけになり、版の数に比例しなくなる。ブラウザ試験の、6 版がそれぞれ別の 1 タイルを持つ文書では、全部読むと 6 件 6330 bytes、この方式では 1 件 1055 bytes だった。
大きな文書の時間とメモリは測っていない。試験の画像は単色で圧縮が効いているため、bytes の絶対値は目安にならない。

## 8. 判断

- 既定を変えない。失敗の現れ方が変わるので、明示オプションにする。
- 読み込みは操作の前に行い、Engine の同期経路を非同期にしない。
- 取り込みと操作を分け、失敗時に文書を変えない。
