## 前提

ベクターは合成パス（`composite.wgsl`）を通らない。文書の `NodeKind::Vector { paths }`（`crates/alto-doc/src/lib.rs:537`）は、エンジンで `RContent::Mesh`（`crates/alto-engine/src/lib.rs:323`）になり、`raw_node` の `RContent::Mesh(paths) => self.vector(VectorContent::Paths(paths), world, roi, true)`（`crates/alto-gpu/src/renderer/m5.rs:1106`）から `vector`（`m5.rs:501-565`）が `VectorResources::render`（`crates/alto-gpu/src/renderer/vector.rs:691`）を呼び、M5 の `rgba16float` のターゲットへ描く。Rust の `gap`（`crates/alto-gpu/src/cpu_composite.rs:2304`、`RContent::Mesh(_) => return Some("vector")` は `:2322`）と JS の `sceneGap`（`tests/e2e/cpu-composite.js:826`）は `"vector"` を返し、parity の `vector-fill`（`tests/e2e/parity-tests.js:351-360`、`M32 32 H200 V200 H32 Z` の赤）は xfail である。

同じ塗りの経路は、ベクターマスクとクリッピングパスのカバレッジも作る。`vector_coverage`（`m5.rs:594-627`）が `path_coverage`（`m5.rs:566-593`）を呼び、白の一本のパスを `VectorContent::Paths` で `vector` に渡し（`batch` は偽）、feather の半径でガウスぼかしを掛ける（`r == 0` ならコピー、`m5.rs:696-699`）。結果は `apply_props` のモード 11（`m5.rs:656-659`、`effects.wgsl:246` の `out=load_a(p)*load_b(p).r`）で掛ける。

今日のずれは次の五つである。

1. **MSAA。** サンプル位置（Vulkan の `standardSampleLocations` は必須でない）、ラスタライザの固定小数の精度（`subPixelPrecisionBits` は 4 以上なら何でもよい）、辺の結びの規則、resolve の平均と丸めは実装が決める。Metal、lavapipe、SwiftShader で一致する理由はない。
2. **Lyon の f32。** テセレーションは f32 の交点と走査で、三角形の分け方そのものが f32 の比較で決まる。Rust の f32 は native と wasm で同じビットになるが、JS に同じ式を書く手段はない（JS は f64）。
3. **超越関数。** 帯は `sqrt` と `log2` と `powi` で決まり、許容差を通して頂点の数を変える。`log2` は正しい丸めを要求されず、libm によって違う。
4. **f32 の頂点と平行移動。** 原点を境界の中心にした f32 の頂点（`lib.rs:403`）と、f64 で引いて f32 にした平行移動を GPU が f32 で掛ける。融合積和（FMA）を使うかは実装が決める。
5. **着色と重ねが f32 とハードウェア。** #24 が決定性の基礎にしないと裁定したものそのものである。経路の選択（Legacy、Batched、Dense）によって、同じパスがどの順の何回の描画で塗られるかも変わる。

JS の参照にはベクターの経路がない。[正確な CPU 参照](2026-10-27-exact-cpu-references.md) の「vector-fill」節（`:41-47`）は、4 つの Q4 のサンプル点で内外を数える案だった。この文書がそれを置き換える。理由は三つある。4 サンプルは縁で 0、64、128、191、255 の 5 段しか出さず、v2 の面積に近い見た目を捨てる。サンプル点の内外判定は、辺の上の点の結びの規則を別に要る。[v3 整数テキスト](2026-10-28-v3-integer-text.md) がすでに Q8 のセル積分（`rasterize_q8`）を定義しており、同じラスタライザを二つ持たない方が保ちやすい。

## 決定：カバレッジは CPU の整数セル積分、GPU は合成だけ

v3 のベクターの塗りは、テキストの `rasterize_q8` を一般化した CPU の整数ラスタライザ一つでカバレッジを作る。GPU は、そのバイトを `textureLoad` と `unorm_byte` で読み、Q14 の整数で着色して重ねるだけである（`unorm_byte` の f32 は「数の境」の唯一の例外）。Lyon、GPU のラスタライザ、MSAA、サンプラ、ハードウェアのブレンドは、v3 の塗りのどこにも使わない。

理由はテキストの「決定」と同じ四つである。一致の対象が CPU の Rust の一つのソースに減る。WGSL のラスタライザは三つ目の実装として割に合わない。ハードウェアのラスタ化は仕様で一意でない。そして字形と塗りで同じラスタライザを共有できる（字形の直接帯は、塗り規則が非ゼロで、点の上限が狭いだけの塗りである）。

三実装の分担は次のとおりである。

| 部分 | WGSL | Rust | JS |
| --- | --- | --- | --- |
| パスの検証と編集 | — | 編集（`alto-vector`、今のまま） | — |
| 座標と色のビット列の整数分解、`WorldQ`、Q8 の点 | — | 本番（参照も兼ねる） | 参照（`cpu-composite.js`、新規） |
| 分割、セル積分、塗り規則、バイト | — | 本番 `raster_q8.rs`（新規、参照も兼ねる） | 参照（`cpu-composite.js`、新規。セルは疎な表で持つ） |
| カバレッジの読み、着色、重ね | 本番（`glyph-q14.wgsl` を共有） | 参照（`cpu_composite.rs`、テストのみ、新規） | 参照（同上） |

テキストと同じく、ラスタ化の Rust は参照と本番が同じ関数で、参照として独立なのは JS である。JS はセルを疎な表で持ち、Rust は密な配列で持つ。二つの実装は「疎と密の同値」（下）で同じ値になる。

## 数の境

v3 の契約（Linus の裁定、#31）：浮動小数は作るとき（編集、前計算）だけ許す。その結果は整数で保存し、描画は整数と文書の値のビット列だけを入力にする。描画には、比較・丸め・正確な積を含め、浮動小数の演算を一つも置かない（GPU の `unorm_byte` だけが例外で、下に理由を書く）。

ベクターの文書の値（座標の f64、色と線幅の f32、node 変換とマスク変換の f64）は、テキストの node 変換と同じく**浮動小数として扱わない**。各値の IEEE-754 のビット列を整数として分解する。したがってベクターには、テキストの焼き込みに当たる新しい保存形式が要らない。文書の JSON と内容ハッシュは v1 / v2 / v3 で同じである。

禁止するもの。v3 の描画での f32 / f64 の演算（`bounds`、`point`、`multiply`、`sqrt`、`log2`、`powi`、比較を含む）、Lyon、`Mesh` のキャッシュの読み、`textureSample`、MSAA、ハードウェアのブレンド。v2 の `c[3] > 0.0` のような浮動小数の比較も v3 では整数の判定に置き換える（下）。JS の参照は BigInt だけで、文書の数はビット列（16 進の文字列）で受け取る。

**例外は一つだけである。** GPU が `R8Unorm` のカバレッジを `textureLoad` で読むと f32 の `b / 255` が返る。WGSL にはこのテクスチャ形式を整数で読む手段がないので、`unorm_byte`（`effects.wgsl:168-169`、`u32(clamp(v, 0.0, 1.0) * 255.0 + 0.5)`）の f32 の `clamp`、積、和でバイト `b` に戻す。これは #31 が「`unorm_byte` のあと整数の加減乗と非負の除算だけ」として認めた例外と同じで、文書の値には掛からず、テクスチャ形式の読みを整数に戻すだけの変換である。256 値すべてで `b` に戻ることは `R8Unorm` の読み取り検査（#31 の実装順の 2、`Gpu::atlas_read`）が 3 バックエンドで確かめ、入れた時点から必須にする。この一か所のほかに、v3 のベクターの描画に浮動小数の演算はない。CPU（Rust と JS）はバイトを整数のまま持つので、この変換もない。

## 座標の系

**`WorldQ` と `RoiQ`。** #31 の定義をそのまま使う。根から node 変換を Q16 の整数で合成し、ベクターノードで一度だけレベルの倍率 `2^L` を掛ける。ベクターのシーンは `L` が −6 まで下がる（`renderer.rs:2071`）ので、`L < 0` では各成分を `v * 2^-L` にする。倍率を掛けた**後**にもう一度、係数 `|m| < 2^31`、平行移動 `|t| < 2^47` を検査し、外れたらそのノードは透明にして診断に `VECTOR_TRANSFORM_RANGE` を出す。#31 の `TEXT_TRANSFORM_RANGE` と同じ扱いである。ベクターマスクとクリッピングパスは、ノードの `WorldQ` にマスクの `transform`（`Affine2`、f64）の Q16 を #31 の合成の式で掛けたものを使う。

**座標の Q16。** パスの各座標 `v` は `text_q16_from_bits(v.to_bits())` で Q16 の `P` にする。検証が `|v| <= 2^20` を保証する（`lib.rs:160-165`）ので、`|P| <= 2^36` で、分解の `k = x + 16` はいつも `-16` 以下である（`k > 9` の拒否は起きない）。`-0.0` は 0 である。

**点の Q8。** レベルの画素の Q8 の点 `G` は

```text
G_x = div_q_i128(W.m[0] * P_x + W.m[2] * P_y + W.t[0] * 2^16, 2^24)
G_y = div_q_i128(W.m[1] * P_x + W.m[3] * P_y + W.t[1] * 2^16, 2^24)
```

である（Q16 × Q16 = Q32、平行移動の Q16 に `2^16` を掛けて Q32、`2^24` で割って Q8）。分子は有理数の値全体で、丸めは一回である。点は `Move`、`Line`、`Quad` の制御点と終点、`Cubic` の二つの制御点と終点で、どれも同じ式で写す。

**パスの原点。** 一つのパス（全サブパス）の全部の点について、

```text
A = (floor_div(min G_x, 256), floor_div(min G_y, 256))     // 整数の画素
L = G - 256 * A                                            // パスの座標。どの成分も 0 以上
```

とする。以下の分割とセル積分は、すべてこの**パスの座標** `L` で行う。#31 の字形の座標と同じ理由（`div_q` の丸めは 0 をまたぐ平行移動で変わる）で、分子をいつも非負にするためである。`A` も `L` も窓に依らない。

**点の上限（証明）。** `|W.m| < 2^31`、`|P| <= 2^36`、`|W.t| < 2^47` から、`G` の分子は `|W.m[0] P_x| + |W.m[2] P_y| + |W.t[0]| 2^16 < 2^67 + 2^67 + 2^63 < 2^69` で、`|G| <= 2^69 / 2^24 + 1 = 2^45 + 1`。`L` は `max G - 256 A <= max G - min G + 255 <= 2^46 + 257 < 2^47` である。この上限は入力の検証だけから出るので、テキストの `L <= 2^24` のような描画時の前提の検査は要らない。どのパスもどの窓でも描かれる。テキストの上限（`2^24`）はテキストの経路に残す（「共有の形」）。

## 色

塗りの色の各チャネル `c`（f32）は、#31 の f32 版の整数分解を `f = 14` で使う。

```text
c_q14 = color_q14_from_f32_bits(c.to_bits())  // #31 の f32 版の手順を f = 14 で。半分は 0 から遠い側。検証で 0 <= c <= 1 なので 0..=16384
```

実数の `floor(c * 16384 + 1/2)` と同じ値で、浮動小数の演算はない。

**`f = 14` が要る理由。** #31 は一般形の `f` を 8 と 16 に限った（text メモ `:205`）。この文書はその制限を、塗りの色の f32 の分解に限って `f = 14` に広げる。座標と変換は #31 のとおり Q8 と Q16 のままで、14 は色にしか使わない。Q8 / Q16 に揃えない理由は三つある。

1. 色の単位は #24 の Q14（`ONE = 16384`）で、着色の式（下の「Q14 への合成」）は Q14 の `c` を直接取る。Q16 で分解してから `div_q(c_q16, 4)` で Q14 にすると二回丸めになり、`c * 16384` が `x + 1/2` の直下の値で `x + 1` を返す（実数の最近は `x`）。Q8 では精度が足りない。
2. テキストの色は焼き込みの `text_color_q14`（#31 `:415`）で、定義は実数の `floor(clamp(c, 0, 1) * 16384 + 1/2)` である。検証済みの `0 <= c <= 1` では、ここの `f = 14` の分解はその定義と同じ値になる。同じ文書の同じ色が、テキストとベクターで同じ Q14 になる。二回丸めではこれが崩れる。
3. ベクターには焼き込みがない（「数の境」）ので、テキストのように編集側の f64 の `round` で Q14 を作れない。描画時にビット列から直接 Q14 を作るには、`f = 14` の整数分解が要る。

実装では #31 の一般形を広げず、別の関数 `color_q14_from_f32_bits`（Rust と JS、新規）として置き、`f = 14` を中に固定する。#31 の `f ∈ {8, 16}` の制限と、その検査はそのまま残る。固定値のテストは「溢れの検査」の色の行である。`c <= 1` なので `k = x + 14` はいつも `-9` 以下で（`c = 1.0` は `m = 2^23`、`x = -23`、`k = -9`）、左シフトも `k > 9` の拒否も起きない。`c = 1.0` は `(2^23 + 2^8) >> 9 = 16384`、`c = 2^-15`（Q14 のちょうど半分、`m = 2^23`、`r = 24`）は `(2^23 + 2^23) >> 24 = 1`、その直下（`m = 2^24 - 1`、`r = 25`）は 0 である。

**塗るかどうか。** v2 は `fill.filter(|c| c[3] > 0.0)`（`lib.rs:442`）で f32 を比べる。v3 は `c_q14[3] == 0` なら塗りを飛ばす。`0 < c_a < 2^-15` の塗りは v2 では描かれ v3 では描かれないが、v3 では描いても `F = 0` で `acc' = acc` なので、飛ばすことは結果を変えない（最適化であって規則ではない）。

## 線

線は v3 の範囲外である（「未解決の問題」の 1）。v3 の文書でも、線の画素を v2 の式から整数へ移すまで、一つのノードの中で v2 の f32 と v3 の Q14 を混ぜない。判定はノード単位で、すべて整数で行う。

```text
stroke_visible(s) = (s.width.to_bits() & 0x7fffffff) != 0  &&  color_q14_from_f32_bits(s.color[3].to_bits()) != 0
```

ノードのどのパスにも見える線がなければ、そのノードは v3 の整数の経路で描く。一つでもあれば、ノード全体を今の v2 の `render`（Lyon と MSAA）で描き、診断に `VECTOR_STROKE_V2` を出す。そのノードの画素は measured-not-enforced で、v3 のハッシュは最終ではない。#26 がベクターマスクを v2 のモード 11 と 12 に残したのと同じ扱いである。`0 < c_a < 2^-15` の線は v3 では見えない線として扱う。

v2 は線を f32 で比べる（`lib.rs:464-466` の `s.width > 0.0 && s.color[3] > 0.0`）。v3 はこの比較を使わず、上のビット列の判定にする。v2 との関係は次のとおりである。

- **線幅。** 検証は `s.width` を有限で `0.0..=4096.0` に限る（`StyledPath::validate`、`lib.rs:271-273`）。この範囲では `(bits & 0x7fffffff) != 0` は `+0.0` と `-0.0` だけを除くので、v2 の `s.width > 0.0` と同じ真偽になる。
- **アルファ。** v2 の `s.color[3] > 0.0` とは `0 < c_a < 2^-15` で違う。v2 はその線を描き、v3 は見えない線とみなしてノードを v3 の経路に残す。v3 の着色では `c_a` の Q14 が 0 になり、描いても画素は変わらないからである（下の「塗るかどうか」と同じ理由）。

## 共有の形

#31 の `rasterize_q8` を、字形と塗りで共有する核 `raster_q8`（`crates/alto-gpu/src/raster_q8.rs`、新規）に分ける。核の引数は次の四つで、字形とパスは定数だけが違う。

| 引数 | 字形（#31） | 塗り（この文書） |
| --- | --- | --- |
| 点の上限 `LMAX`（パスの座標 `L` の各成分） | `2^24`（描画時に検査し、超えたら描かない） | `2^47`（上の証明で常に満たす。検査は表明だけ） |
| 分割数の上限 `NMAX` | 64 | 4096 |
| 上限で足りない曲線 | `NMAX` に切る（#31 のまま） | パスを拒否する（`VECTOR_CURVE_RANGE`、下の「曲線の分割」） |
| 塗り規則 | 非ゼロ（セル積分） | 非ゼロ（セル積分）、偶奇（副走査線の交点の偶奇、下の「塗り規則とバイト」） |

核の分割数の判定は、`NMAX` 以下に満たす `n` がなければ `None` を返す。字形の包みは `None` を #31 どおり 64 にし、塗りはパスを拒否する。`glyph_atlas.rs` の `rasterize_q8`（#31）は `raster_q8(…, LMAX = 2^24, NMAX = 64, Clamp, NonZero)` の薄い包みになる。字形のバイトは #31 の定義と同じで、核の中の算術の幅が i128 に広がっても、値は同じである（整数の式は幅に依らない）。

## 曲線の分割

#31 の「曲線の分割」と同じ式で、上限を `NMAX = 4096` にし、上限で足りない曲線の扱いを変える。`D` を二階差分の Q8 の長さの二乗（二次は `P0 - 2C + P1`、三次は `P0 - 2A + B` と `A - 2B + P1` の大きいほう）とし、`n` は 1..=4096 で

```text
65536 * n^4 >= K^2 * D        (二次 K = 10、三次 K = 30)
```

を満たす最小の整数とする。左辺は `n` について単調なので、線形の探索でも二分探索でも同じ `n` になる。比較は u128 で行う。この `n` では弦の誤差はいつも約 1/40 画素以下である。

**上限の境。** `n` で足りる二階差分の長さ（レベルの画素）は 上の式 `65536 * n^4 >= K^2 * D` から `sqrt(D) <= 256 * n^2 / K`、すなわち `sqrt(D) / 256 <= n^2 / K` で出る（`n = 256` で `2^16 / K`、`n = 4096` で `2^24 / K`）。`K` が二次と三次で違うので、境も二つある。

| `n` | 二次（`K = 10`） | 三次（`K = 30`） |
| --- | --- | --- |
| 256（v3 の初版の上限） | `2^16 / 10 ≈ 6554` 画素 | `2^16 / 30 ≈ 2185` 画素 |
| 4096（`NMAX`） | `2^24 / 10 ≈ 1_677_722` 画素 | `2^24 / 30 ≈ 559_241` 画素 |

`NMAX = 256` のままでは、三次で約 2185 画素、二次で約 6554 画素を超える曲線の誤差が 1/40 画素を超え、レベル −6 の半径 1500 の円（四分円の三次の二階差分が約 `0.46 * 1500 * 64 ≈ 44_000` 画素、要る `n` は約 1150）がそれに当たる。そこで上限を 4096 まで上げて**さらに分割**し、それでも足りない曲線は**明示的に拒否**する。

**拒否。** パスのどれかの曲線で 1..=4096 のどの `n` も式を満たさない（三次で二階差分が約 559_241 画素、二次で約 1_677_722 画素を超える。レベル −6 では文書の画素で三次が約 8738、二次が約 26_214）なら、そのパスは描かない。塗りならそのパスを飛ばし（ほかのパスは描く）、ベクターマスクやクリッピングパスならそのカバレッジは全画素 0 になる。診断に `VECTOR_CURVE_RANGE` を出す。判定はパスの全部の曲線の `D` で行い、下の「結果を変えない省略」で分割しない曲線も `D` だけは計算する。`D` はパスの点と `WorldQ` とレベルだけで決まるので、拒否は窓とタイルに依らない（あるタイルだけ欠けることはない）。レベルには依るので、同じパスがレベル −5 で描かれ −6 で拒否されることはある。上限に切って描く（#31 の字形の形）ことはしない。誤差が 1/40 画素の保証を外れた画素を、黙って enforce の値にしないためである。

分割点は #31 と同じく Bernstein の整数形を一回だけ割る。`i = 1..=n` について

```text
二次: q = div_q_i128((n-i)^2 * P0 + 2 (n-i) i * C + i^2 * P1, n^2)
三次: q = div_q_i128((n-i)^3 * P0 + 3 (n-i)^2 i * A + 3 (n-i) i^2 * B + i^3 * P1, n^3)
```

で、`L` が 0 以上なので分子は非負である。分子は凸結合の `n^k` 倍で、丸めた点は制御点の凸包の x と y の範囲（整数の端）の中にある。`i = n` は終点そのものである。線分は、`Move` のたびに開いた輪郭を閉じる線、`Close` の閉じる線、末尾で閉じる線を含め、#31 と同じく `cur != start` のときだけ出す。比較は Q8 の整数で行う。v2 の Lyon は開いたサブパスを `builder.end(false)`（`lib.rs:410`、`:438`）で閉じずに渡すが、塗りの走査はどのみち閉じた多角形として扱うので、閉じる線を足すことは塗りの意味を変えない。

## カバレッジ（セル積分）

#31 の「カバレッジ（セル積分）」と同じ式を、パスの座標 `L` で行う。違いは三つだけである。

1. **幅。** 行と列の分割の分子（`x0 * (y1 - y0) + (x1 - x0) * (Y - y0)` と `ya * |xb - xa| + (yb - ya) * |X - xa|`）は i128 で計算し、`div_q_i128` で割る。商は `L` の範囲に入るので i64 に戻す。
2. **窓。** 窓は、パスの全部の点の `L` の境界を外側へ画素に丸め（`floor_div` と `ceil_div`）、`A` を足してレベル画素にし、ROI の `[ox, ox + w) × [oy, oy + h)` と交わらせた矩形である。交わりが空ならそのパスは描かない。窓の左上をパスの画素座標で `(lx, ly)`、幅と高さを `ww`、`wh` とする。`XL = 256 lx`、`XR = 256 (lx + ww)`、`YT = 256 ly`、`YB = 256 (ly + wh)`。
3. **塗り規則。** セル積分を使うのは非ゼロだけである。偶奇は同じ線分の列から副走査線の交点を作る（下の「塗り規則とバイト」）。

セル `(cx, cy)` の `cover` と `area`（i64、初期値 0）、行の分割、列の分割、窓の左の小片を `XL` に切ること、窓の右の小片を捨てること、`cover += dir * dy`、`area += dir * (fa + fb) * dy`、行の前置和 `S` と `N = S * 512 - area` は、すべて #31 の文のとおりである。

**窓の独立性。** #31 の議論がそのまま成り立つ。点 `G`、原点 `A`、分割数、分割点、行と列の境での値は、パスだけで決まり窓に依らない。したがって、タイルの継ぎ目でパスが割れても、両側の画素は一枚で描いた場合と全バイト一致する。レベル −6 で数十万画素に広がるパスも、256 画素のタイルごとに同じ値を切り出す。

**結果を変えない省略（証明つき）。** 曲線と線分のうち、窓に寄与しないものは分割しなくてよい。どれもパスの点だけで判定し、結果のバイトは省略しない場合と同じである。

- **窓の上か下。** 制御点の凸包の y の範囲が `[YT, YB]` と交わらない（`max y <= YT` か `min y >= YB`）なら、その曲線を捨てる。丸めた分割点は凸包の y の範囲の中にあるので、どの小片も行の範囲の外で、#31 の規則で捨てられる。
- **窓の右。** 凸包の `min x >= XR` なら捨てる。すべての小片が `XR` 以上で、寄与しない。
- **窓の左。** 凸包の `max x <= XL` なら、曲線をその弦 `P0 → P1` の一本の線分に置き換える。窓の左の小片は `ua = ub = XL` に切られ、`cx = 0`、`fa = fb = 0` なので、`area` には何も足さず、`cover[0, cy]` に `dir * dy` を足すだけである。一本の連続な折れ線について、行 `cy` の帯 `[Ycy, Ycy + 256] ∩ [YT, YB]` への `dir * dy` の和は、y を帯に切った値の差 `clamp(y_end) - clamp(y_start)` に等しい（各線分の項 `clamp(y1) - clamp(y0)` が隣と打ち消し合う）。この値は端点だけで決まるので、分割した折れ線と弦は同じ `cover` を足す。

偶奇（下の副走査線の交点）でも三つの省略は結果を変えない。副走査線の高さ `y_s` は `YT + 8` 以上 `YB - 8` 以下なので、凸包が窓の上か下にある曲線はどの副走査線とも交わらない。凸包の `min x >= XR` の曲線の交点はすべて `XR` 以上で、偶奇は左から数える（下）ので、窓の中の画素の偶奇を変えない。凸包の `max x <= XL` の曲線は、交点がすべて `XL` 以下で、窓の中の点 `x >= XL` から見るとその個数の偶奇だけが効く。半開の規則では、一本の連続な折れ線が `y_s` と交わる回数の偶奇は「始点と終点の一方だけが `y > y_s`」と同じで、端点だけで決まる。したがって弦と同じである。

省略は性能のためで、規則ではない。Rust も JS もどちらを選んでもよく、`raster_q8_skips_are_exact`（新規）が省略あり・なしの全バイト一致を見る。

## 塗り規則とバイト

二つの規則は、どちらも画素ごとの `0 <= e <= 131072`（131072 が完全な被覆）を作り、同じ式でバイトにする。

```text
byte = (e * 255 + 65536) >> 17
```

結びは `e = 65536` のときだけ（255 と 2^16 は互いに素）で、`byte = 128` は 0 から遠い側である。

**非ゼロ。** セル積分の `N`（i64）から `e = min(|N|, 131072)` とする。`N / 131072` は画素の符号付きの巻き数の面積で、#31 と同じく `|winding|` を 1 で切る近似である。

**偶奇は巻き数の偶奇で決める。** `N` は使わない。`N` は巻き数の面積の**和**で、偶奇は和から決まらないからである。同じ形・同じ向きの二つのサブパスの共有する辺をまたぐ画素は、辺の内側の巻き数が 2、外側が 0 でどちらも偶（塗らない）なのに、`N = 2 * 65536 = 131072` になる。`N` を周期 2 で折り返す形（FreeType の gray ラスタライザの偶奇）はこの画素を 255 にし、縁に暈（halo）を出す。v3 はこの形をとらず、点ごとの巻き数の偶奇が奇である部分の面積を、次の整数の手順で数える。

1. **副走査線。** 窓の行 `cy`（`0 <= cy < wh`）を 16 本の副走査線に分ける。`j = 0..16` の副走査線の高さは、パスの座標の Q8 で `y_s = YT + 256 * cy + 16 * j + 8` である。`y_s` は Q8 の整数で、窓の位置ではなくパスの画素の行だけで決まる（`YT + 256 cy` はパスの画素の行の上端）。
2. **交点。** 分割後のすべての線分（窓の外のものも含む。省略は上の三つだけ）について、端点を `ya < yb` の順に並べ替えた `(xa, ya)`、`(xb, yb)` とする。`ya <= y_s < yb` のとき（半開。水平な線分は交わらない）、交点を一つ出す。

   ```text
   x = div_q_i128(xa * (yb - ya) + (xb - xa) * (y_s - ya), yb - ya)
   ```

   分子は `x` の実数値の `yb - ya` 倍で非負、分母は正で、丸めは一回である（列の分割の式と同じ形）。線分の向き `dir` は使わない。
3. **偶奇。** 副走査線の交点の値の多重集合を `X` とし、点 `x`（Q8 の整数の位置 `[x, x + 1)`）の偶奇を `π(x) = #{ x_i ∈ X : x_i <= x } mod 2` とする。同じ値の交点の並びの順は `π` を変えない。閉じた輪郭（「曲線の分割」で閉じる線を足すので、輪郭はいつも閉じる）は半開の規則で各副走査線と偶数回交わるので、`π` は窓の右で 0 に戻る。左から数えるので、窓の右より先の交点は窓の中の `π` に効かない。
4. **画素の面積。** 画素 `(cx, cy)` の `T` を、16 本の副走査線について `#{ x ∈ [XL + 256 cx, XL + 256 cx + 256) : π(x) = 1 }` を足したものとする（u32、`0 <= T <= 16 * 256 = 4096`）。実装は交点を昇順に並べ、`π = 1` の区間 `[x_1, x_2)`、`[x_3, x_4)`、… を `[XL, XR)` に切って、各画素の列との重なりの長さを足す。
5. `e = 32 * T`（`T = 4096` で 131072）。

この手順では、同じ値の二つの交点（向きが同じでも逆でも）は幅 0 の区間になり、何も足さない。したがって同じ形・同じ向きの二つの図形が辺を共有しても、その辺の画素に暈は出ない（下の `vector_even_odd_shared_edge`）。線分の向きを使わないので、向きを全部反転したパスも同じバイトになる。窓の独立性は非ゼロと同じ理由で成り立つ（`y_s`、交点、`π`、画素の列はパスだけで決まる）。

整数の辺と Q8 の半画素の辺は、偶奇と非ゼロで同じバイトになる。副走査線は `16 j + 8` にあるので整数の水平な辺の上に乗らず、`M32.5 32.5 H200.5 V200.5 H32.5 Z` の上の辺の行は 16 本のうち 8 本が内側で `T = 2048`、`e = 65536`、`byte = 128`、角は `T = 8 * 128 = 1024`、`byte = 64` である。斜めの辺では、非ゼロは正確な面積、偶奇は 16 本の副走査線の和なので、重なりのない図形でも縁のバイトが規則によって違うことがある（「未解決の問題」の 6）。

v2 の Lyon は塗り規則を三角形の組で厳密に解き、縁の部分被覆を MSAA が近似する。v3 の非ゼロは、同じ向きに重なるサブパスの縁で v2 より濃くなる（二枚の同じ正方形の縁の画素は、巻き数の面積 1/2 + 1/2 で 255）。v3 の偶奇は点ごとの巻き数の偶奇で、重なりの縁は巻き数が 2 の部分を塗らない。どちらも v3 の定義であり、v2 に合わせない。

## 疎と密の同値

「疎と密」には二つの意味があり、どちらも v3 の画素を変えない。

**1. セルの持ち方。** Rust の本番は窓の `ww × wh` の密な `cover` と `area` を持つ。JS の参照は、触れたセルだけを `(cy, cx)` の表に持ち、各行を `cx` の昇順に走る疎な形で書く。触れないセルの `cover` と `area` は 0 なので、前置和 `S` への寄与も 0 である。各セルの値は小片の寄与の整数の和で、整数の和は結合的で可換なので、足す順と持ち方は値を変えない。行の前置和は `cx = 0` から右への順で、密では全セルを、疎では触れたセルだけを走るが、間のセルでは `S` が変わらず `area = 0` なので `N = 512 S` が続く。疎な形では、触れたセルの間の画素にこの値を埋める。したがって両者の `N` は全画素で同じである。偶奇はセルを持たず、Rust も JS も副走査線ごとの交点の列から `T` を作る。交点の値は線分ごとに決まり、`π` は並べる順に依らないので、二つの実装の `T` も全画素で同じである。

**2. 描画の経路。** v2 の `VectorMode`（Legacy、Pooled、Disjoint、Dense、Batched）、`batch::plan` の並べ替え、`dense_candidate` と `Dense` の 8 枚の MRT は、v3 では一つも使わない。v3 のホストは `mode` を読まず、パスの順（`paths` の順。v2 の `Mesh` の順と同じく、塗りは各パスの中で線より先）にインスタンスを並べ、`glyph-q14.wgsl` が画素ごとにその順で重ねる。画素の値はインスタンスの列だけで決まる。

- チャンクの切り方（`GLYPH_Q14_CHUNK`、スクラッチの区切り）は、中間が Q14 の u16 で損失がないので結果を変えない（#31 と同じ理由）。
- 将来、画素の矩形が交わらないパスをまとめる（v2 の Disjoint の考え）、あるいは 8 本ずつ MRT のように並行に処理しても、ある画素を覆うインスタンスの順が保たれる限り同じ値になる。矩形がその画素を含まないインスタンスは、その画素では恒等だからである。
- 検査 `vector_mode_does_not_change_v3_pixels`（新規）は、`set_mode` の五つと `dense_candidate` が真になる 8 本以上の重なりのシーンで、ノードの Q14 が全バイト一致することを見る。

## Q14 への合成

パスの塗り一つは、#31 の字形一つと同じ式である。`b` をカバレッジのバイト、`k = byte_q14(b)`、`c` を塗りの Q14 のストレート RGBA とする。

```text
F     = k * c_a                          // 0..=2^28
s_a   = div_q(F, 16384)
s_rgb = div28(c_rgb * F)                 // プレマルチプライ Q14、一回丸め
acc'  = div_q(s * 16384 + acc * (16384 - s_a), 16384)     // #24 の normal、全チャネル
```

`acc` の初期値は 0 で、`b = 0` の画素は恒等である。`c_rgb <= 16384` から `s_rgb <= s_a`、`acc_a <= 16384` と `acc_rgb <= acc_a` から `acc'_a <= 16384` と `acc'_rgb <= acc'_a` である（#24 の normal の証明と同じ）。結果のノードは M5 の v3 の中間（`rgba16uint`、プレマルチプライ Q14）である。透明な背面への normal は Q14 のコピーなので、parity の単独のベクターのタイルは `div_q_i64(acc * 255, 16384)` である。

**例。** `M32 32 H200 V200 H32 Z` の赤（`[1, 0, 0, 1]`）は、整数の辺なので内側の画素が `N = 131072`、`b = 255`、`k = 16384`、`acc = (16384, 0, 0, 16384)`、タイルのバイトは `(255, 0, 0, 255)`、外側は 0 である。辺を 32.5 にずらすと縁の画素は `N = 65536`、`b = 128`、`k = (128 * 16384 + 127) / 255 = 8224`、`s = (8224, 0, 0, 8224)`、タイルのバイトは `div_q_i64(8224 * 255, 16384) = 128` である。

## ベクターマスクとクリッピングパス

v3 の文書で feather が 0 のベクターマスクとクリッピングパスは、上のラスタライザのバイトをそのままカバレッジにする。`k = byte_q14(b)` が #26 のモード 11 の `k` で、`out = div_q(a * k, 16384)` である。feather の判定は `mask.feather.to_bits() & 0x7fffffff == 0` で、浮動小数を比べない（クリッピングパスは今も feather 0 で `path_coverage` を呼ぶ、`m5.rs:611-617`）。

**マスクとクリップの順。** ベクターマスクとクリッピングパスの両方があるノードでは、二つのカバレッジを先に合わせ、ソースには一度だけ掛ける。これが規範の順である。

```text
k_m = byte_q14(b_mask)、k_c = byte_q14(b_clip)
k   = div_q(k_m * k_c, 16384)        // 両方あるとき。一方だけならその k
out = div_q(a * k, 16384)            // モード 11、全チャネル
```

今の v2 も同じ順である。`vector_coverage`（`m5.rs:594-627`）がマスクのカバレッジにクリップのカバレッジをモード 11 で掛けて一枚にし（`:618-621`）、`apply_props`（`m5.rs:656-659`）がそれをモード 11 で一度だけソースに掛ける。ソースへ順に掛ける `div_q(div_q(a * k_m, 16384) * k_c, 16384)` は丸めが二回になり、`div_q(a * k, 16384)` と 1 LSB 違うことがあるので使わない。`k_m * k_c` は可換なので、マスクとクリップのどちらを先に読むかは値を変えない。合わせた `k` は Q14 のまま持ち、バイトに戻さない（シェーダの中で二つのバイトを読んで合わせるか、Q14 の中間に書くかは実装 PR が選ぶ。値は同じである）。ノードの不透明度とラスタのマスク（モード 4）はその前で、`apply_props` の順（モード 4、次にモード 11）を変えない。ベクターマスクの feather が正なら、クリッピングパスも含めてそのノードの二つのカバレッジはどちらも v2 の `path_coverage` のままにし、v2 と v3 を混ぜない。

白の一本のパスを `vector` に通す今の `path_coverage` の形はとらず、カバレッジのバイトを `R8Unorm` のスクラッチに置き、モード 11 の v3 が `textureLoad` + `unorm_byte` で読む。

feather が正のマスクは、ガウスぼかしの v3 が入るまで v2 の `path_coverage` のままで、measured-not-enforced である。入ったあとは、ここのバイトの Q14 をぼかしの入力にする（「未解決の問題」の 5）。

## スクラッチとシェーダ

#31 の「アトラスとスクラッチ」と「着色と重ね」をそのまま使う。パスの窓のバイト（`ww × wh`、窓はいつも ROI の中）を `R8Unorm` のスクラッチに `queue.write_texture` で置き、`GlyphQ14 { dst, src, tex = 1, color }` のインスタンスを一つ作る。容量で区切るとき、`GLYPH_Q14_CHUNK` に達したときは、そこまでを一つのディスパッチにして**新しい**スクラッチで続ける。同じテクスチャを使い回さない理由（`write_texture` は後のコマンドバッファより先に実行される）も #31 と同じである。各テクスチャは `check_allocation` で `Class::Vector` の予算に数え、足りなければ今の `render` と同じくエラーを返す。

一つのノードにテキストとベクターは同居しない（`RContent` は一つ）ので、アトラス（`tex = 0`）は使わない。シェーダは #31 の `glyph-q14.wgsl` を一文字も変えずに使い、名前も変えない。`glyph_q14_uses_effects_helpers`（#31）が写した補助関数の一致を見る。

## JS の入力

JS の参照は文書の値のビット列から始まる。wasm にテスト用の要求 `vectorBits`（`#[wasm_bindgen(js_name=vectorBitsForTesting)]`、`packages/alto-sdk/src/worker.ts` の `readTileLevel` と同じ並びに case を足す。#31 の `textBake` の隣）を足す。引数はノードの ID で、返すのは次のものである。

- 根からそのノードまでの各 node 変換の f64 のビット列（16 進）。#31 の `textBake` と同じ形。
- 各パスの各コマンドのタグと、座標の f64 のビット列（16 進）。
- 各パスの `fill` の f32 のビット列（16 進、None は null）、`fill_rule`、線の幅と色のアルファの f32 のビット列。
- ベクターマスクとクリッピングパスの各座標、`transform`、`feather`、`fill_rule`、`enabled`。

JS は文書のスナップショットの JSON の数を読まない。その先、ビットの分解、`WorldQ`、Q8 の点、原点、分割、セル積分（疎な表）、塗り規則、バイト、着色、重ね、出力のバイトはすべて JS が BigInt で独立に計算する。除算は `divQBig` である。JS は返った値を、スナップショットのパスの数とコマンドの数とタグの並びと突き合わせ、違えば失敗する。

## 溢れの上限

上限は解析で、標本ではない。入力の上限は、検証の `|v| <= 2^20`（座標）、`0 <= c <= 1`（色）、1 パス 4096 コマンド、`WorldQ` の `|m| < 2^31`、`|t| < 2^47`（レベルの倍率の後も検査する）である。そこから「座標の系」の証明で `|P| <= 2^36`、`|G| <= 2^45 + 1`、`0 <= L < 2^47` が出る。一つのパスの線分の数 `Sg` は、各コマンドが高々 `NMAX = 4096` 本（`Move` と `Close` は閉じる線一本。`NMAX` で足りない曲線のパスは拒否するので、分割数はいつも 4096 以下）、末尾で一本なので `Sg <= 4096 * 4096 + 1 = 2^24 + 1` である。

| 項 | 上限 | 入る型 |
| --- | --- | --- |
| `WorldQ` の合成（#31） | 係数 `2^63`、平行移動 `2^92` | i128 |
| レベルの倍率 `v * 2^-L`（`L >= -6`） | `2^31 * 64 = 2^37`、`2^47 * 64 = 2^53`（この後で `2^31`、`2^47` を検査） | i64 |
| 点 `G` の分子 | `2^67 + 2^67 + 2^63 < 2^69` | i128 |
| `G`、`L` | `|G| <= 2^45 + 1`、`L < 2^47` | i64 |
| 二階差分の成分 | `2 * 2^47 = 2^48` | i64 |
| `D` | `2 * 2^96 = 2^97` | u128 |
| `K^2 * D`（`K = 30`） | `900 * 2^97 < 2^107` | u128 |
| `65536 * n^4` | `2^16 * 4096^4 = 2^64` | u128（u64 には入らない） |
| Bernstein の分子 | 非負。係数の和 `n^3 <= 2^36` で `2^36 * 2^47 = 2^83` | i128 |
| 行の分割の分子 | 各項 `< 2^47 * 2^47 = 2^94`、和 `< 2^95` | i128 |
| 列の分割の分子 | `ya * |dx| < 2^94`、`dy * |X - xa| <= 2^8 * 2^47 = 2^55`、和 `< 2^95` | i128 |
| 小片の `(fa + fb) * dy` | `512 * 256 = 2^17` | i32 |
| セルの `area` | `Sg * 2^17 <= (2^24 + 1) * 2^17 < 2^42` | i64 |
| セルの `cover` と行の前置和 `S` | `Sg * 256 < 2^33` | i64 |
| `N = S * 512 - area` | `2^42 + 2^42 = 2^43` | i64 |
| 偶奇の交点の分子 | 非負。`xa * (yb - ya) + (xb - xa) * (y_s - ya)` は `x * (yb - ya)` で `< 2^47 * 2^47 = 2^94` | i128 |
| 偶奇の交点 `x`、副走査線 `y_s` | `[0, 2^47)` | i64 |
| 一本の副走査線の交点の数 | `Sg <= 2^24 + 1` | u32 |
| 偶奇の `T`、`e = 32 * T` | `T <= 4096`、`e <= 131072` | u32 |
| バイトの `e * 255 + 65536` | `131072 * 255 + 65536 = 33_488_896` | u32 |
| 着色と重ね（#31） | `F <= 2^28`、`c_rgb * F + 2^27 <= 2^42 + 2^27`、重ねの分子 `<= 2^28 + 8192` | u32、`Wide`、i32 |

**証明の補足。** セルの `area` の上限は、一本の線分が一つの行の中では x について単調で、各セルに高々一つの小片しか落とさないことに依る。窓の左は列の境を作らないので、`XL` に切られる小片は行ごとに一本の線分から一つである。`S` の上限は、一本の線分が一つの行へ足す `|dy|` の和が 256 以下であることに依る。偶奇の `T` は、各副走査線で画素の列の長さ 256 を超えないので、`Sg` に依らず 4096 以下である。行と列の分割の商と偶奇の交点は、端点の凸結合の丸めなので `[0, 2^47)` に入り、i64 に戻してよい。ラスタ化は CPU だけなので i128 は Rust の `i128` と JS の BigInt だけで、WGSL は #31 の着色の一項だけが `Wide` を使う。

## 溢れの検査

テスト名は `vector_q8_raster_does_not_overflow` で、`raster_q8.rs` のテストに置く（新規）。#31 の `text_q8_raster_does_not_overflow` と同じく、上の各項を `checked_mul` / `checked_add` で計算し、`None` か表の上限の超過で失敗する。

- 座標の端点 `{-2^20, -1, -2^-16, 0, 2^-16, 1, 2^20}` と `WorldQ` の端点 `{-(2^31 - 1), -1, 0, 1, 2^31 - 1}`、`{0, ±(2^47 - 1)}`、レベル `{-6, 0, 12}` の直積で、`G` の分子、`G`、`L` が上限以下であること。
- パスの座標の端点 `{0, 1, 255, 256, 257, 2^47 - 256, 2^47 - 1}` の直積で、二次と三次の二階差分、`K^2 * D`、Bernstein の分子を `n` の 1..=4096 の全数で見る。分割数の整数の判定が、f64 で正確な範囲の `D` で `(K * sqrt(D) / 256).sqrt().ceil()` と一致し、それが 4096 を超える `D` で `None` になることも見る（テストの中だけの f64）。
- 分割数の境を固定値で見る。`65536 * n^4 = K^2 * D` のちょうどの `D` と、その 1 上の `D` で、二次と三次のそれぞれ `n = 256` と `n = 4096` の境（約 6554 / 2185 画素、約 1_677_722 / 559_241 画素）。`n = 4096` の境の 1 上の三次を一本含むパスが描かれず、`VECTOR_CURVE_RANGE` を出し、同じノードのほかのパスは描かれること。
- 行と列の分割の分子と偶奇の交点の分子を同じ端点で見る。#31 の `intersection_q8_rounds_coordinate` の固定値（`(257,0)-(256,512)` の `Y=256` が 257 など）が、i128 の版でも同じ値になること。
- `Sg = 2^24 + 1` 本の線分を一つのセルに重ねる最悪の場合（同じ縦線を往復させ、分割数がちょうど 4096 になる 4096 コマンドの三次の曲線の列）を構成し、`area`、`S`、`N` と、一本の副走査線の交点の数が上限以下であること。
- バイトの式を、非ゼロは `N` の `{0, 1, 65535, 65536, 65537, 131071, 131072, 131073, 262144, 2^43 - 1}` とその符号反転で、偶奇は `T` の `{0, 1, 2047, 2048, 2049, 4095, 4096}` で見る。偶奇は `T = 2048` が 128、`4096` が 255。
- 色の Q14 の分解 `color_q14_from_f32_bits` を、`{0.0, -0.0, 2^-15 の直下, 2^-15, 2^-15 の直上, 0.5, 1.0}` の f32 のビット列で Rust と JS の両方で見る。期待値は `0, 0, 0, 1, 1, 8192, 16384`。#31 の一般形が `f = 14` を受けないこと（制限が残ること）も見る。
- 着色と重ねは #31 の `glyph_q14_does_not_overflow` を共有する。

単体テストはほかに六つ足す。

- `raster_q8_matches_glyph_raster`。#31 の `rasterize_q8` の単体テストの字形を、核 `raster_q8` の字形の定数で描いたバイトが全バイト一致する（共有で字形の値が変わらないこと）。
- `vector_q8_window_crop`。一つのパスを大きな窓で描いた結果と、2×2 に割った四つの窓の切り出しが全バイト一致する。窓の境がパスの中を通る場合、曲線の分割点が境の上に乗る場合、窓の左端がパスの点の 1 画素右にある場合（#31 の `P0 = (255, 0)`、`C = (256, 15)`、`P1 = (255, 0)`）、パスの広がりが `2^24` を超える場合を含む。
- `raster_q8_skips_are_exact`。上の三つの省略を入れた場合と入れない場合のバイトが、窓の上・下・左・右にはみ出す曲線と、窓の左で何度も上下する三次の曲線で全バイト一致する。
- `vector_fill_rules`。五芒星（自己交差）で、非ゼロは中心が 255、偶奇は中心が 0。外側を時計回り、内側を反時計回りにした二つの正方形で、非ゼロも偶奇も穴が 0。同じ向きの二つの正方形で、非ゼロは穴がなく 255、偶奇は重なりが 0。向きを全部反転したパスで、偶奇のバイトが変わらないこと。
- `vector_even_odd_shared_edge`。同じ形・同じ向きの二つの図形が辺を共有する場合を、Rust の参照 `vector_q14` のバイトと照合する（JS の参照は同じパスを parity の `vector-v3-shared-edge` で照合する）。期待値は手で求めた固定値で、`N` を折り返す形なら 255 になる画素を必ず含む。
  - (a) 同じ正方形 `M32.5 32.5 H200.5 V200.5 H32.5 Z` を二つのサブパスで重ねる（同じ向き、四辺すべてを共有）。偶奇は全画素 0（内側の巻き数 2、縁の画素も 2 と 0）。非ゼロは内側 255、角を除く辺の画素も `|N| = 2 * 65536 = 131072` で 255。四つの角の画素（`(32, 32)`、`(200, 32)`、`(32, 200)`、`(200, 200)`）は各正方形が 1/4 画素だけ覆うので `|N| = 2 * 32768 = 65536` で 128（偶奇は角も 0）。
  - (b) `A = M32.5 32.5 H200.5 V200.5 H32.5 Z` と `B = M96.5 32.5 H200.5 V200.5 H96.5 Z`（同じ向き。右、上、下の辺を共有）。偶奇は、列 33..=95 の内側が 255、列 32 と列 96 が 128（半画素だけ巻き数 1）、列 97..=200 が 0（列 200 は巻き数 2 の半画素と外側）。上の行 32 は、列 33..=95 が 128、列 32 と 96 が 64、列 97..=200 が 0。非ゼロは列 33..=199 の内側が 255、列 32 と 96 は内側で 128 と 255、列 200 は 255（`|N|` を 1 で切る近似）。
  - (c) 正方形を二つ隣り合わせる（`M32.5 32.5 H96.5 V200.5 H32.5 Z` と `M96.5 32.5 H160.5 V200.5 H96.5 Z`、同じ向き。共有する辺 `x = 96.5` で向きは逆）。偶奇も非ゼロも、列 96 は内側の行（33..=199）で 255 で、継ぎ目が出ない。上の行 32 と下の行 200 の列 96 は縦に半画素だけ覆うので、どちらの規則でも 128 である（偶奇は 16 本のうち 8 本で `T = 2048`、非ゼロは `N = 65536`）。
- `vector_mode_does_not_change_v3_pixels`（上の「疎と密の同値」）。

## 一致の期待

## enforce と measure

enforce するのは、構成上一致し、3 バックエンドの CI で全バイト一致したケースだけである。上の表で enforce と書いたものは、実装 PR で一致を確かめてから通常のケースとして入れる。期待どおりに一致しなかったら measure に落とさず、設計に戻る（#24 のアトラス読み取りと同じ扱い）。`R8Unorm` の読み取り検査（#31 の実装順の 2）は、入れた時点から必須である。

measure するのは、v2 の `vector-fill`、v3 の文書の線、feather が正のマスクである。`measureRow` と `formatMeasure` で `measure: true, enforced: false` の行にし、失敗にしない。v2 の計測は「前提」の 1 から 5 のどれが効いているかを分けるため、native では `set_mode` の五つの値の行を持つ（ブラウザは既定のモードだけ。「未解決の問題」の 9）。

## 未解決の問題

1. **線。** v3 の文書でも線は v2 のままである。整数にする案は二つある。(a) 線の輪郭（結合、端点、マイタの制限）を編集のときに浮動小数で作り、整数の多角形として文書に保存して、描画は非ゼロの塗りにする（Linus の裁定の「作るときだけ浮動小数」に合う。#31 の焼き込みと同じ形）。(b) 描画時に整数だけで輪郭を作る（丸い結合と端点に整数の円弧の分割が要る）。(a) は拡大で丸い結合が多角形に見える。どちらにするかは別の設計で決める。
2. **カバレッジの精度。** 塗りはテキストと同じくバイト（`R8Unorm`）を通る。`N` から Q14 を直接作る（`(e * 16384 + 65536) >> 17`、`R16Uint` のスクラッチ）と縁の階調が細かくなるが、テキストと別の式になり、#31 の読み取り検査と別のテクスチャ形式が要る。今は共有を選んだ。
3. **分割数の上限。決定済み。** `NMAX = 4096` で、足りない曲線のパスは `VECTOR_CURVE_RANGE` で拒否する（「曲線の分割」）。拒否の境（三次で約 559_241、二次で約 1_677_722 レベル画素）は、レベル −6 では文書の画素で三次が約 8738 で、`|v| <= 2^20` の文書なら届く。届いたパスを `NMAX` に切って描く案（誤差は大きいが決定的）は、1/40 画素の保証を外れた画素を enforce の値にするのでとらなかった。拒否が実際の文書で問題になるなら、曲線を整数の de Casteljau で二等分してから分割する形（分割点の丸めが変わるので別の定義になる）を別の設計で考える。上の「窓の上・下・右・左の省略」で、窓に関係しない曲線は分割しない（`D` だけを計算する）ので、費用は窓に掛かる曲線だけで決まる。
4. **CPU の費用とキャッシュ。** タイルごと、レベルごとに CPU でラスタ化し直す。128 パス・16384 コマンドのレイヤで、ズーム中の初回の描画がどれだけ遅くなるかは計測していない。窓の独立性があるので、パスごとの大きなビットマップを切り出すキャッシュを足してもよい。v2 の `Mesh` のキャッシュに当たるものを足すかは計測してから決める。`NMAX = 4096` では一つのパスの線分が `2^24 + 1` 本まで増え、偶奇は副走査線ごとに交点を並べる。最悪の場合の費用も同じ計測で見る。
5. **feather が正のベクターマスク。** ガウスぼかしの v3（`v3-blur-design`、未マージ）の入力の形（Q14 の中間か、バイトか）に依る。ぼかしの設計が決まってから、ここのバイトをどう渡すかを決める。
6. **非ゼロの近似。** `|winding|` を 1 で切る近似は、同じ向きに重なるサブパスの縁を v2 より濃くする。厳密な非ゼロ（サブパスの和集合の面積）には、セル積分の代わりに区間の走査が要る。v3 では近似を定義とした。文書の見た目の差が問題になるかは、measure の v2 の行で見る。偶奇は逆に点ごとの偶奇で正確だが、縦の分解能が副走査線の 16 段である。重なりのない図形の斜めの辺では、非ゼロ（正確な面積）と偶奇のバイトが違うことがある。副走査線を増やす（64 本で `T <= 16384`、`e = 8 * T`）と差は小さくなるが費用が増える。非ゼロも同じ副走査線の形にすると二つの規則が揃うが、字形のバイト（#31）が変わるので、字形の核と分けることになる。どちらも計測してから決める。
7. **核の置き場所。** #31 は `rasterize_q8` を `glyph_atlas.rs` に置くとした。この文書は共有の核を `raster_q8.rs` に分ける。#31 の実装順の 1 が先に入った場合の移動の PR を、その実装順の 1 に含めるか、この文書の 1 にするかは、先に入る側の PR で決める。字形のバイトはどちらでも変わらない。
8. **古いメモの指し先。** [正確な CPU 参照](2026-10-27-exact-cpu-references.md) の「vector-fill」節（Q4 のサンプル）は、この文書で置き換えた。あの節からこの文書への指し先は、実装 PR で足す。この変更は文書を一つ足すだけで、既存の文書は触らない。
9. **ブラウザでのモードの切り替え。** SDK にはモードを切り替える要求がなく、wasm では計測用の `vector_probe.rs`（`crates/alto-wasm/src/vector_probe.rs:592-600` が五つのモードを回す）だけが `set_mode` を呼ぶ。SwiftShader で五つのモードの v3 の一致を見るために、テスト用の要求を足すか、`vector_probe.rs` の形を v3 に広げるかは決めていない。v3 のホストはモードを読まないので、決定性の議論には影響しない。
