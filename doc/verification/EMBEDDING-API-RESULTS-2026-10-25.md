## 最後の見直しで直した点

それぞれ、直す前のビルドで失敗するテストを先に書き、直した後に成功することを確かめた。

- 入れ替わった文書の操作口（`DocumentHandle`）が、新しい文書を編集できてしまっていた（古い操作口の `undo()` が、新しい文書を取り消した）。今は `CONFLICT`（`document-closed`）で拒む。
- 全体の表示（保存のたびに届く）で、すべてのノードが新しいオブジェクトになっていた。今は、変わっていないノードを使い回す。
- 1 回の編集で、購読者への通知が 2 回届いていた。Worker が同じ状態を、通知と返信の 2 回送るため。今は 1 回だけ届く。
- 開始できなかったストロークが、毎フレームエラーを報告していた（テストでは 11 回）。今は 1 回だけ報告して終わる。
- 表示倍率に、描画器が描ける範囲（デバイスのピクセルで 0.01〜128）の制限がなかった。範囲を超えると、ポインターの位置と画面がずれていた。

- **B8 が約半分になった。** 古い SDK は編集のたびに、文書の全ノードを複製して凍結し、`change` イベントを 2 回出していた。Playground の画面は、そのたびに作り直されていた。新しい SDK は、変わったノードだけを作り、通知も 1 回にした。組み込み先の画面の作り直しが、そのぶん軽くなる。
- **B3 は結論が出ていない。** 3 回の計測で、作業前と作業後の中央値は次のとおりだった（ms）。
  - 1 回目：16.0 と 21.7
  - 2 回目（8 回ずつ）：20.0 と 20.0
  - 3 回目：18.2 と 20.7

  作業前は値のばらつきが大きく（11.7〜22.1 ms）、作業後は 19.5〜21 ms に集まっている。3 回をまとめると、作業後が p95 で 1〜2 ms 遅い可能性がある。原因はまだ特定していない。ストロークの経路（`ToolSession.flush` と毎フレームのループ）は、送る内容を変えていない。後続の課題とする。
- **同期の参照経路（C2 / C3 の参照）** は、比較のための診断用の経路で、利用者の操作では使わない。C2 は 6% 遅く、C3 は 12% 速くなった。どちらも 3 回の計測で同じ向きだった。
- B4 は、2 回目の計測で 10% 遅かった（3.3 → 3.7 ms）。上の「1 回の編集で通知が 2 回」を直した後の 3 回目の計測では、差は誤差の範囲（3.3 → 3.4 ms）になった。

## 残した点の片付け（2026-10-25）

### B3 の遅れの調査

B3（ブラシ入力から表示まで p95）は、30 回の計測の p95 で、上から 2 番目の値にあたる。この値は、ズームを変えた直後の最初の 1〜2 フレームで決まる。

- **ストロークだけを測った場合**（4K・20 レイヤー、300 回 × 4 回ずつ交互）：
  - 作業前：p50 3.0 ms、p95 7.9 ms
  - 作業後：p50 3.1 ms、p95 8.2 ms
  - 入力を送る時間と Worker の CPU 時間にも差はなかった。
- **B1・B2 の後に B3 と同じ順で測った場合**（6 回ずつ交互）：
  - 30 回の p95 は、どちらのビルドでも回ごとに 18〜25 ms に散らばった。
  - 作業前：18.3〜22.8 ms
  - 作業後：18.3〜25.4 ms
  - 120 回をまとめた p95 は、作業前 10.7 ms、作業後 11.1 ms。
- **結論：** 先に見えた B3 の遅れは、30 回の p95 という計測そのもののばらつきで、コードの変化によるものではない。コードは変えていない。

### 戻る・進むのキャッシュ

ページがキャッシュに入ると、記録を持つエンジンは Worker を止め、保存場所の名前の鍵を手放す。ページが戻ると、鍵を取り直して記録から立て直す。文書の操作口と表示位置は保たれる。戻ったとき、鍵がほかのタブに取られていれば `failed` になり、`retry()` で立て直せる。組み込みのテストに 2 件を加えた（`PageTransitionEvent` を送って確かめる）。

### 画像の書き出し

- 表示タイルを、64 枚ずつ 1 回の GPU の読み戻しで読むようにした。
- `scale` が 1/2 以下のときは、ピラミッドの段から読むようにした（段ごとに枚数が 4 分の 1 になる）。
- 4K・20 レイヤーでの時間（少ない回数の目安）：

  | 場合 | 作業前 | 作業後 |
  |---|---|---|
  | 最初の書き出し（倍率 1） | 641 ms | 475 ms |
  | 2 回目以降（倍率 1） | 約 105 ms | 約 78 ms |
  | 2 回目以降（倍率 0.25） | 約 94 ms | 7 ms |
  | 倍率 1 の直後の倍率 0.25 | 102 ms | 411 ms |

- 最後の場合だけ遅くなった。以前は、直前の書き出しで作った等倍のタイルを読み直していた。今は、縮小した段のタイルを最初から作る。
- 縮小した段だけを書き出す場合（サムネイル）は、作業前も等倍のタイルを最初から作る必要があったので、今のほうが速い。
- 組み込みのテストに、倍率 0.5 の書き出しがピラミッドの 1 段目の表示タイルと一致することの確認を加えた。
