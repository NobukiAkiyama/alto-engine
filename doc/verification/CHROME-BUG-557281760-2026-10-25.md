# Chrome の不具合の調査：crbug.com/557281760 との照合（2026-10-25）

前回の報告：[GPU-LOSS-RESIZE-TRIGGER-2026-10-25.md](GPU-LOSS-RESIZE-TRIGGER-2026-10-25.md)。その後の対策：[FRAME-PACING-RESULTS-2026-10-26.md](FRAME-PACING-RESULTS-2026-10-26.md)。

## 判定

- **同じ症状の公開報告がある。** [crbug.com/557281760](https://issues.chromium.org/issues/557281760)「WebGPU: resizing a worker-owned canvas while the GPU is behind loses the device」。
  - 2026-09-05 に登録された。
  - Chromium の確認担当が、M142〜155 の Windows・Linux・macOS で再現を確かめた。
  - 状態は Assigned、P2 / S2。修正の変更はまだない（Gerrit で番号を検索して 0 件）。
- **ログの文言は、こちらの喪失と一致する。**
  - `non-existent mailbox` → `Error: 4 for Command kDissociateMailboxForPresent` → `A valid external Instance reference no longer exists`
  - 違いは 1 点だけ。報告は GPU アダプタなので `ProduceDawn`、こちらは SwiftShader（CPU アダプタ）なので、Skia を経由する `ProduceSkia` になる。
- **報告の再現条件では、こちらの環境では再現しなかった。** Alto を使わない再現（`tests/diagnostics/behind-resize*`）を、CI で 21 分間走らせた。macOS、Chrome 156.0.8078.47、SwiftShader で、約 9,000 回のサイズ変更をしても、喪失は 0 回だった。報告では 6 分間の試行が 5 回中 5 回とも、0〜110 秒で喪失している。
- したがって、**同じ不具合である可能性は高いが、確定はしていない。** 同じ内部の失敗（表示用の画像の ID が GPU プロセス側にない）に、別の引き金で入っている可能性がある。

## 1. 報告の内容（要約）

- 条件：Worker の OffscreenCanvas から、`requestAnimationFrame` のたびに表示する。描画は 1 vsync より重い。前のフレームが GPU で終わる前に、`canvas.width/height` が変わる。
- 対照（どれも喪失しない）：
  - メインスレッドで同じ処理をする
  - 負荷を軽くする
  - GPU で処理中のフレームが 1 枚ある間は次を出さない（`inflight=1`）
- 報告者の推測：`SharedImagePool::Reconfigure` が、表示へ送られている途中の古い大きさの画像を消す。
- Chromium 側のコメント（cwallez）：「サイズ変更で画像の再利用が止まり、メモリ不足になったのでは」という推測。担当者が割り当てられたところで止まっている。

## 2. Chromium 156 のコードを読んで分かったこと

対象：`webgpu_swap_buffer_provider.cc`、`shared_image_pool.{h,cc}`、`gpu_canvas_context.cc`、`offscreen_canvas.cc`、`canvas_resource_dispatcher.cc`、`exported_canvas_resource.cc`、`canvas_resource.cc`、`client_shared_image.cc`。いずれも 156.0.8078.47。

- **報告者の推測は、コードとそのままは合わない。**
  - pool が持つのは、表示から返ってきた後の、使っていない画像だけ。
  - 表示へ送った画像は、返却の callback（`MailboxReleased`）が参照を持ち続ける。だから `Reconfigure` → `ClearInternal` では消えない。
  - 返ってきた画像の大きさが変わっていれば、pool には戻さずに破棄する。破棄は、表示側から返された sync token を待つ。
- 現在の描画バッファを捨てる処理（`DiscardCurrentSwapBuffer`）は、その画像をいったん pool に戻す。次の `getCurrentTexture` で大きさが違えば、そこで破棄される。破棄は、WebGPU 側の利用終了の sync token を待つ。順序の誤りは、読んだ範囲では見つからなかった。
- 共有画像の sync token の自動管理（`kUseAutomaticSyncTokenManagement`）は、2026 年 9〜10 月に開発中の変更が多い。ただ、デバッグ用の有効化の変更ばかりで、既定は無効とみられる。今回の原因かは確かめていない。
- 結論：**クライアント側（renderer）のコードからは、画像が早く消える経路を特定できなかった。** GPU プロセス側の記録（mailbox の ID 付き）がないと決められない、という前回の判断は変わらない。

## 3. Alto を使わない再現（CI）

`lifecycle_implementation=chrome-repro`。どの条件も新しい文書で 90 秒ずつ走らせた。

- 描画：GPU 負荷を調整できる重い fragment shader で別のテクスチャに描き、それを表示用のテクスチャに写して submit する。
- サイズ変更：40 ms ごとに 60 px ずつ幅を変え、端で 300 ms 止まる。高さも 3 px 変える（Playground と同じ揺れ）。
- サイズの受け渡し：ResizeObserver（`device-pixel-content-box`）が大きさを送る。

- 報告の「GPU が遅れたまま表示を続ける」状態は作れた（処理中のフレームが最大 24 枚、完了まで最大約 0.9 秒）。それでも、こちらでは失われなかった。
- 報告との違いで、残っているもの：
  - 報告は実際の GPU で、表示用の画像は IOSurface などの本物の GPU メモリになる。こちらは SwiftShader で、Skia を経由する
  - キャンバスの大きさ：報告は約 5000×2494、こちらは最大 1800×1000
  - 表示の有無：報告はヘッドありの表示、こちらは headless
- **Alto での喪失は、どれも起動直後だけで起きている**（前回の報告の 7 件）。起動直後に特有の何か（最初の表示の準備、WASM の初期化と重なる負荷など）が要るのかもしれない。これはまだ確かめていない。

## 4. 事実・仮説・未確定

- 事実：
  - 公開の不具合報告と、ログの文言が一致する。
  - 報告では、Worker のキャンバスで、GPU が遅れているときにサイズを変えると喪失し、処理中を 1 枚に抑えると喪失しない。
  - Alto の起動中の描画は、`tick()` を続けて呼び、GPU の完了を待たずに表示する。
  - Alto でサイズ変更の前に GPU の完了を待つと、4 回中 3 回だった喪失が 3 回中 0 回になった（前回の記録。数が少ない）。
  - 報告の条件をなぞった、Alto を使わない再現は、こちらの環境では 0 回だった。
- 仮説：
  - Alto の喪失と crbug.com/557281760 は、同じ内部の不具合である。
  - 処理中のフレームの数を抑える（back-pressure）と、どちらも防げる。
- 未確定：
  - Chromium の内部で、どの画像がなぜ早く消えるのか。
  - こちらの環境で、Alto なしで再現する条件。
  - Chromium がいつ直すか。

## 5. Chromium の報告に足せる情報（投稿は未実施）

次の英文を、報告の追記の候補として残す。投稿には Google アカウントでのサインインが要る。

> Same signature on Chrome for Testing 156.0.8078.47, macOS 15 (GitHub Actions), WebGPU on SwiftShader (CPU adapter, so the decoder goes through AssociateMailboxUsingSkiaFallback): `ProduceSkia: Trying to Produce a Skia representation from a non-existent mailbox` → `Error: 4 for Command kDissociateMailboxForPresent` → device lost, "A valid external Instance reference no longer exists". GPU process stays alive. In our app it happens only during startup, 19–400 ms after the worker's OffscreenCanvas height changes (e.g. 412↔415) while frames are presented back to back without waiting for onSubmittedWorkDone: 8/15 runs. Debouncing the resize brought it to 0/15; waiting for queue completion before the resize also avoided it in our small sample. A plain-JS repro following this report's steps (worker rAF, heavy fragment shader, ResizeObserver device-pixel-content-box, up to 24 frames in flight, ~9,000 resizes over 21 minutes) did not reproduce it on SwiftShader, so a real GPU / IOSurface-backed swap buffers may matter. Reading the 156 sources, in-flight swap buffers are held by MailboxReleased callbacks rather than the pool, so SharedImagePool::Reconfigure alone does not seem to destroy them.
