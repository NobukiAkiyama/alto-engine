# CI の GPU 喪失：起動直後のキャンバスのサイズ変更が引き金（2026-10-25）

構造化した証拠：[gpu-loss-resize-trigger-ci-2026-10-25.json](gpu-loss-resize-trigger-ci-2026-10-25.json)。

それまでの調査（GPU-LOSS-INVESTIGATION / ISOLATION / SURFACE-RECORDING、`codex/gpu-loss-ci` ブランチ）を引き継いだ。

## 判定

- **Alto 側の引き金は特定した。** 起動直後の数秒間に Worker の OffscreenCanvas の大きさが変わると、Chrome 156 の表示用 SharedImage（mailbox）の取り込みが失敗し、デバイスを失う。
  - 大きさが変わる原因は 2 つ：
    - Playground の状態表示の行が、日本語と英数字の切り替えで 3 px 伸び縮みすること（970×412 ↔ 415）
    - 起動時のパネルの表示と非表示（412 → 314 → 412/415）
  - サイズ変更を 100 ms まとめて適用し、状態表示の行の高さを固定した変更（e4a3b5d）で、同じ条件の CI で喪失しなくなった：
    - 修正なし：15 回中 8 回で喪失
    - 修正あり：15 回中 0 回
- **ブラウザ内部の根本原因は特定していない。** mailbox が「作られる前に参照された」のか、「早く破棄された」のか、「別の mailbox を参照した」のかは、通常の Chrome のログと記録では決められない。Chrome の不具合を回避したもので、直したものではない。

## 1. 比較（同じ CI 条件、交互に実行）

条件：
- 実行方式：`gpu_lifecycle=true`、`lifecycle_implementation=sdk`、`surface_recording=true`
- 環境：Chrome for Testing 156.0.8078.47、macOS、WebGPU は SwiftShader
- 基準：`codex/gpu-loss-ci` の b3b70c1
- 修正あり：同じものに e4a3b5d を加えた `claude/gpu-loss-debounced`（29ca9f0 / 207b713）

試験の合否ではなく、ブラウザのログに `non-existent mailbox` か `SURFACE-FAILURE` があるかで、喪失を数えた。

| 条件 | 実行 | 喪失した実行 |
|---|---|---|
| 基準 | 15 | 8 |
| 修正あり | 15 | 0 |

- **偶然の可能性：** 修正に効果がないとして、8 回の喪失がすべて基準側に入る確率は約 0.1%（片側 Fisher の正確検定）。
- **修正ありの赤い実行について：** 赤くなった実行は、私が追加したちらつきの試験の上限（2 回）が、遅い CI に対して厳しすぎたもの（3〜6 回）。GPU の喪失ではない。上限は 4fa30a4 で 10 回に直した（修正前は 59 回）。
- **それ以前の基準側の結果：**
  - 引き継ぎ時：4 回中 3 回
  - 同日の別の比較：6 回中 1 回、6 回中 0 回

  合わせると 31 回中 12 回。頻度は時間帯で変わるので、交互の比較を主な根拠にした。

## 3. 否定した仮説

- **Rust の `wgpu::Instance` / `Adapter` の解放：** デバイスの寿命のあいだ持ち続けても（35be75a）、喪失は続いた。「external Instance」という文言は、デバイスを失った結果として出るもので、原因ではない。
- **サイズ変更のたびの `surface.configure()`：** Chromium の `GPUCanvasContext::configure` は、swap buffer provider を無効化して作り直す。そこで、Web では configure を呼ばずにキャンバスの大きさだけを変える実験をした（`claude/gpu-loss-no-reconfigure` の c20d89a）。
  - 表示は正しかった：4 通りの大きさのスクリーンショットで、2,200〜3,800 点の照合の食い違いは 0。Metal と SwiftShader の両方で確かめた。
  - それでも喪失した：6 回中 3 回（同時の基準は 6 回中 1 回）。引き金は configure ではなく、大きさの変更（`OffscreenCanvas::SetSize` → `Reshape`）の側にある。この変更は採用しない。

## 4. サイズ変更の前に GPU の完了を待つか

負荷試験：`tests/diagnostics/resize-stress.js`。`claude/gpu-loss-debounced`（207b713）の `lifecycle_implementation=resize-stress`。
- 8 枚の半透明レイヤー（3072×2048）を、パンと描画で動かし続ける。
- その最中に、本物のサイズ変更を 40 回行う。それぞれ 100 ms のまとめ時間より長く保つ。

| 条件 | 実行 | 喪失 | サイズが描画バッファに届くまで p50 / p95（ms） |
|---|---|---|---|
| 待たない | 6（240 回の変更） | 0 | 155〜174 / 206〜286 |
| `gpuIdle()` を待つ | 6（240 回の変更） | 0 | 247〜446 / 375〜778 |

- 起動後のサイズ変更は、負荷の下でも喪失しなかった。弱いのは、起動直後の短い期間だと考えられる。
- GPU の完了を待つと、反映が大きく遅れる。まとめ時間を入れた後では、効果が観測できない。**製品には入れない。**

## 5. Chromium のコードから分かること（156.0.8078.47）

- Worker で `width` / `height` を変えると、`OffscreenCanvas::SetSize` が `frame_dispatcher_->Reshape` と `GPUCanvasContext::Reshape` を呼ぶ。後者は、現在の描画バッファを捨て（`DiscardCurrentSwapBuffer`）、pool の画像の大きさを変える。
- 新しく作る SharedImage は `creation_sync_token` で、再利用する画像は解放時の sync token で待つ（`shared_image_pool.cc`）。クライアント側に、順序の明らかな誤りは見つからなかった。
- `ProduceSkia` の「non-existent mailbox」は、サービス側の管理表に mailbox がない分岐（`shared_image_manager.cc`）。release ビルドには、mailbox の ID を出すログもトレースもない。

起動直後だけ弱い理由は、まだ分からない。候補は、表示側のフレーム受け渡し（`frame_dispatcher_` の Reshape）が初期化を終える前にサイズが変わる、といったものだが、確かめていない。

## 6. 残っていること

- ブラウザ内部の原因（A / B / C）を決めるには、mailbox の登録・取り込み・破棄を ID 付きで記録する、計測入りの Chromium が要る。
- 組み込む側のアプリが、起動直後に本当にキャンバスの大きさを変える場合、同じ条件になりうる。今回の対策（まとめ時間 100 ms）は、その場合の頻度を下げるが、なくしはしない。CI では、Playground とテストで、その状況が起きないことを確かめた。
- 確かめたのは macOS、Chrome 156、SwiftShader の組み合わせだけ。
