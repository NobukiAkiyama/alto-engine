# 4K 半透明レイヤーの性能ボトルネック（2026-10-22）


生の検証JSONはこのディレクトリに置かない。新しい実行は CI の artifact `alto-browser-reports`（GPU lifecycle の手動実行は `gpu-lifecycle-<OS>`）、ローカルは gitignore した `verification/out/`。以下のかつてのファイル名は、この変更より前の git 履歴にある。

対象: `026ff48`、Chrome 155 headless、Apple Metal WebGPU、3840×2160 のラスターレイヤー。通常ベンチマークは 20 層。比較のため同じシーン生成ループを一時的に 10 層にし、計測後に元へ戻した。Worker / SDK に加えた一時的な時計計測も元へ戻した。記録は 20 層（`profile-translucent-20-layers-2026-10-22.json`、CI artifact `alto-browser-reports`、ローカルは `verification/out/`） と 10 層（`profile-translucent-10-layers-2026-10-22.json`、CI artifact `alto-browser-reports`、ローカルは `verification/out/`）。各条件 1 回の診断ランであり、細かい差を評価するための統計試験ではない。

## 確認できた主因

1. **復旧時の全オブジェクト検証。** 20 層ランの Worker 再起動は 891.6 ms、そのうち `recover()` は 807.9 ms。Worker 起動は 76.2 ms、保存データの取得は 1.6 ms、記録の replay は 0 ms（0 件）で、`runtime.openPackage()` が 799.8 ms を占める。`alto-store::decode_entries` は ZIP 内の各オブジェクトを `decode_object` で伸長してハッシュを検証する。圧縮済み checkpoint が約 4.94 MB でも、4K×20 層のタイルを全件処理するため時間がかかる。単純に検証を省く修正はデータ完全性を損なう。
2. **未キャッシュの半透明タイルの合成。** B2 の約 395 ms のうち `runtime.tick` の同期処理が約 313 ms。B7 初回描画の約 1138 ms のうち約 868 ms。半透明レイヤーは不透明レイヤー用の下層省略条件を満たさず、各表示タイルで全層をたどる。`compose` は既存の低解像度表示キャッシュを使えない場合、各レイヤーの元タイルを取得し、アトラスへ転送して合成する。復旧直後は表示キャッシュとアトラスが空で、元タイルの LZ4 展開も必要になる。
3. **少量の残り時間は Worker 往復とフレーム分割。** 20 層 B2 は `runtime.tick` 外に約 82 ms、B7 初回描画は約 270 ms。`waitFrame` は 8 ms の仕事量を指定し、重いタイルでも最低 1 枚は合成する。20 層時は B2 が 12 tick、B7 が 11 tick に分かれた。`gpuIdle()` の末尾待ちはそれぞれ約 1.7 ms、3.5 ms。ただし GPU 実行が CPU と重なるため、これだけで GPU シェーダー負荷をゼロとは断定できない。

## 次に手を入れる順序

1. 復旧経路の `openPackage` を細分化し、ZIP 読み出し、全オブジェクト伸長・ハッシュ検証、インストールを個別計測する。可視タイルを先に安全に検証して開き、残りを段階的に検証する設計が可能か調べる。
2. `compose` の内側で、タイル取得・LZ4 展開、RGBA コピー、`queue.write_texture`、コマンド生成、GPU 提出を個別計測する。まず最も高い部分を減らす。縮小時には完成済み表示タイルからの pyramid 利用率も記録する。
3. 20 層の B2/B7 を固定した回帰ベンチマークで確認する。10 層だけが目標を満たしても、20 層の性能問題は残る。

B1 の移動中フレームは 20 層でも p95 約 3.4 ms で、温まった表示キャッシュを使う通常移動は主な問題ではない。問題は縮小時と復旧直後のコールドパスに集中している。
