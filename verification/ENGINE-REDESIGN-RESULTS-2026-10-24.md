# 訂正と追加調査（2026-10-24）

## B6 の WASM のメモリ

上の表の「170.1 MiB（−29%）」は、エンジン本体の WASM だけの値だった。第 2 段階の B で加えた展開 Worker の WASM メモリと、受け渡し中のバッファを含めていない。これらを含めて測り直すと、展開側の最大値は 52.5 MiB で、エンジン本体の 170.1 MiB との和（総量の上限）は 222.6 MiB になる。作業前の 241.1 MiB（展開 Worker なし）より少ないが、減少幅は −29% ではなく −8%（上限で比べた場合）である。B6 は現在、この上限を記録する。

## CI で時々起きた失敗

- **症状：** M5 の最後のテストで、表示タイルの読み戻しのバッファのマップが失敗した（CI の push の実行、SwiftShader、Chrome 152）。手元の遅い環境（`taskpolicy -c background`）では、8 回中 2 回、エンジン Worker が panic した。panic の内容は、wgpu の WebGPU 実装（`backend/webgpu.rs:2461`）の `unwrap()` で、`createBuffer failed, size (144) is too large for the implementation when mappedAtCreation == true` だった。
- **原因：** wgpu の WebGPU 実装では、バッファやテクスチャを Rust 側で捨てても何もしない（`Drop` の中身が空）。JS の GPU オブジェクトは、JS のガベージコレクションが回収するまで残る。描画器は、タイルを合成するたびに `mappedAtCreation` 付きの小さなバッファを作り、読み戻しのたびにマップ付きの 256 KB のバッファを作っていた。これらのマップ用の共有メモリが、回収されるまで溜まり、遅い環境では確保に失敗していた。
- **対策：** 合成ごとのバッファは `mappedAtCreation` を使わずに作り、`queue.write_buffer` で書き込む。読み戻しのバッファは、使い終わったら `destroy()` で解放する。ストロークのテクスチャは、確定時とキャンセル時に `destroy()` で解放する。
- **対策（追加）：** ほかにも、捨てても解放されない GPU オブジェクトがあった。合成・効果・ベクター・ブラシの描画ごとに作る uniform やコマンドのバッファ、作り直した効果用のテクスチャ（`M5 ROI target`）、作り直したベクターのカバレッジ用テクスチャ、キャッシュから追い出したベクターのメッシュ、文書の切り替えで捨てる効果用・ベクター用の資源である。これらは描画器の一覧（`Retired`）に登録し、使うコマンドを送信した直後に `destroy()` する。WebGPU は、送信済みの処理が使い終わるまで実際の解放を待つ。
- **効果：** 機能テストの組を流す間の Chrome のプロセスのメモリの合計の最大値（SwiftShader、各 1 回）：作業前 2141 MiB、対策前 2260 MiB、最初の対策後 2077 MiB、追加の対策後 2030 MiB。
- **遅い環境での再現の試み（`taskpolicy -c background`、SwiftShader、全組を 8 回ずつ）：** 対策前は 8 回中 2 回 panic した。最初の対策後は panic がなくなり、8 回中 1 回、ストロークの確定時の読み戻しでマップが失敗した。
- **ストロークの読み戻しの失敗：** 表示タイルの読み戻しと同じく、デバイスを失っていれば `GPU_LOST`、そうでなければ `INTERNAL` と、読み戻したタイル数を報告する。失敗したときは、ブラシのツールの状態を解除する。以前は解除されず、その後の編集がすべて `CONFLICT` で拒否されていた。
